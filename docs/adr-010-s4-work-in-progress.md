# S4: промежуточный Linux reader, интеграция S3 не выполнена

База: `b7de99ca9dd585aa8f06d3e95e54bfe1d3c50c19` (S1–S2).
Ветка: `spike/linux-v5-s4`. Это **не готовый S4**. Публичного API и CLI нет.
Модули закрыты внутри crate и доступны для сборки через `experimental-v5-reader`.
DDL S2 не меняется. `ValidatedSnapshot` не используется.

## Выполнено в этом срезе

- Входной абсолютный путь открывается покомпонентно через `openat` и закреплённые
  дескрипторы каталогов; `O_NOFOLLOW` на каждом шаге, финальный файл
  `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`, проверка обычного файла и размера.
- Обязательный абсолютный staging должен существовать, принадлежать текущему UID
  и иметь 0700; родители проверяются по политике R09. Корневой sticky-каталог
  допускается только при UID 0. Проверки не ослаблены для песочницы.
- Уникальная exclusive копия 0600, ограниченное потоковое копирование и SHA-256;
  лимит передаёт доверенный вызывающий код, значения production по умолчанию нет.
  Суммы имени и optional expected должны совпасть между собой и с содержимым.
- RAII удаляет только свою копию, включая частичную при ENOSPC; writer закрывается
  до удаления. Reader закрывает соединение перед удалением своей копии.
  Остатки аварийных сессий `bslens-v5-reader-<pid>-<counter>.sqlite` пользователь
  удаляет вручную из выбранного staging; массовой автоочистки нет.
- SQLite получает только путь проверенной копии, read-only; затем query_only ON
  и trusted_schema OFF. Реестр sqlite_schema сравнивается с неизменённым DDL S2,
  включая SQL таблиц/индексов и autoindex; лишние views/triggers отвергаются.
  Проверяются версии, известный профиль, metadata ID и FK.
- `source` использует range.sql и incremental BLOB с ограничением объёма ответа;
  `tree` использует branch.sql, включая статус непринятого BSL.

## Точная граница координации с S3

`src/linux_v5_reader.rs::SharedFacts` — временный **закрытый** интерфейс:

```rust
fn facts_sha256(&self, connection: &rusqlite::Connection) -> Result<String, String>;
fn compatible_scope(&self, connection: &rusqlite::Connection) -> Result<(), String>;
fn verify_saved_sources(&self, connection: &rusqlite::Connection) -> Result<(), String>;
```

S3 должен предоставить общую каноническую функцию хеша и повторно используемое
построение фактов из сохранённых XML/BSL. Реализаций этих функций здесь нет.
`verify_saved_sources` обязан сверять хеши источников и воспроизводить объекты,
владельцев, методы и физический индекс тем же расчётом, что сборщик.
Иной scope_id сам по себе не отказ; нужна проверка совместимости его контракта.
Offline verify не подтверждает Git-происхождение.

После появления ветки S3: обновить **только эту** ветку обычным merge/rebase без
force push; подключить общие функции и удалить временный интерфейс/allow(dead_code).
Уточнить формат snapshot_id по реализации S3 (сейчас staging проверяет префикс,
а reader — точное равенство metadata). Добавить публичный API/CLI только после
полного интеграционного теста: S3 build → open → tree/source → offline verify.
Нужны негативные тесты профиля/ID/FK/фактов и формально целых неверных фактов,
которые open принимает, а общий offline verify отвергает.

## Проверки и ограничения

Синтетические unit-тесты покрывают неверный SHA и очистку до SQLite, две сессии,
подмену входного пути после/во время копирования, рост файла сверх лимита,
частичную запись с ENOSPC, симлинк промежуточного/финального компонента, каталог,
FIFO без блокировки, права staging, схему/v4 и source/tree непринятого BSL.
Тест source/tree создаёт факты вручную: он **не** является интеграцией S3.

Rust 1.85.1 из официального дистрибутива установлен только в облачном workspace;
SHA-256 архива проверен. В файловой песочнице UID `/` и `/tmp` отображается как
65534 и строгая проверка родителей отказывает. Синтетические проверки запускаются
в штатном облачном окружении вне этой песочницы, где оба каталога имеют UID 0.
Реальный корпус, NucBox, Windows, MCP и v4-миграция не используются.
