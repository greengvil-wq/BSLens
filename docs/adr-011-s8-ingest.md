# S8a: ограниченный ingest точного Git commit/tree (синтетический срез)

База: `5c91f662ba6a398e841ba51b39cb3b6cd3d22c55`, ветка
`spike/linux-v5-s8-ingest`. Проверенная среда: Rust 1.85.1, Linux x86_64.

## Что реализовано и куда НЕ подключено

Отдельный feature `experimental-v5-ingest` открывает
`git_manifest::ingest::ingest(repo, commit, expected_tree, limits, consumer)`.
Это библиотечный opt-in API, без CLI/MCP/server-команды. S3 `snapshot_v5::build`,
`derive_facts`, S4 reader/verify, `xml221`, R09 `Manifest::read` и их профили
не переключены на новый код. Полученный `Receipt` не является v5 snapshot или
`ValidatedSnapshot`. Никакой совместимости с БСП/ERP этот срез не доказывает.

Переиспользованы приватные R09 `object_store`, `process::Shell`, проверка полного
OID и Git-хеширование. Реализация R09 и значения его лимитов не изменены.
Репозиторий читается через локальные Git objects; working tree, refs и исходный
config не являются источником истины. Частные `cat-file --batch`/окружение,
запрет replace/lazy fetch, alternates/http-alternates/promisor и symlink-объектов
наследуются. Сетевые источники не открываются. Наследуется ограничение layout:
обычный каталог `.git/objects`, не bare/worktree `.git`-файл. Защита от конкурентной
подмены локального object store/полная hostile-FS изоляция не заявляется.

1. Принимаются только полные lowercase SHA-1/SHA-256 OID одинаковой длины.
   Проверяется исходный commit OID, первая запись `tree`, граница заголовка/тела
   commit, совпадение с обязательным `expected_tree`, исходные OID всех деревьев.
2. До первого callback проверяется весь манифест: типы записей, UTF-8 имена,
   дубликаты внутри дерева, запрещённые компоненты/символы, глубина, длины путей.
   Разрешены только деревья и режимы `100644`/`100755`; symlink/gitlink отвергаются.
   Все регулярные tracked пути входят в отсортированный манифест (включая невыбранные).
   Режим дерева не доказывает наличие/тип тела НЕвыбранного blob: его намеренно
   не читаем. Это инвентаризация записей проверенного дерева, не fsck всех объектов.
3. Выбор фиксирован: чувствительные к регистру суффиксы `.xml` и `.bsl`.
   До callback заранее проверяется остаточный бюджет числа чтений всех выбранных
   путей. Затем blob читается по исходному OID, сверяется тип и Git OID,
   вычисляется SHA-256 исходных bytes и передаётся `(Entry, sha256, &[u8])`.
   SHA-256 здесь вычисленный digest проверенных Git bytes, а не сверка с внешним
   манифестом SHA-256. Для snapshot потребуется сохранять и повторно проверять его.
4. Потребитель вызывается по одному файлу, по bytewise порядку UTF-8 путей.
   Тело освобождается перед следующим файлом. Сохраняются ограниченные метаданные
   манифеста, а не весь корпус; повторяющийся OID читается/учитывается за каждый путь.
   Tree body освобождается перед спуском в дочерние деревья. Временные копии для
   Git-хеширования и протокола остаются ограниченными размером одного объекта.

## Лимиты и ошибки

Нет неявных production defaults: вызывающий передаёт все `Limits`.
Каждое значение положительно и не выше встроенного потолка:

| Измерение | Потолок |
|---|---:|
| entries (включая записи каталогов) | 100 000 |
| trees (включая корневое) | 20 000 |
| reads (commit + деревья + выбранные blobs) | 120 001 |
| object_bytes (в том числе каждый источник) | 16 MiB |
| total_bytes (сумма тел всех прочитанных объектов) | 1 GiB |
| deadline | 300 секунд |
| глубина дерева | 64 |
| UTF-8 bytes полного пути | 1 024 |

Обход layout также наследует отдельные R09 потолки: 100 000 filesystem entries,
глубина 64. Они не подняты и могут стать следующим ограничением loose object store.
Потолки среза — ограничение эксперимента, не результат замера реальной БСП.

Счётчики entries/trees/reads проверяются до следующего действия. Перед чтением
тела backend получает `cap=min(object_bytes,total_bytes-used)`, проверяет заголовок
(не более 128 bytes), тип/OID/каноническую длину и отказывает до выделения большого
тела. Поэтому агрегат не превышается даже на последнем объекте. Сумма включает
commit/tree overhead, а не только исходники. Нулевой остаток допускает пустой blob.

`InvalidLimit{name}` обозначает неверную настройку; `Limit{name,maximum,actual}` —
точно измеренный превышенный счётчик; `Read{oid,code,cap,budget}` — отказ backend с
OID, переданным пределом и ограничивающим бюджетом (`object_bytes`/`total_bytes`).
Унаследованный `Code::Limit` backend также может означать некорректный заголовок,
поэтому фактический размер не выдумывается. `Git(Code)` сохраняет ошибки identity,
path, layout и timeout; `Consumer(String)` — отказ приёмника.

Один абсолютный дедлайн действует на layout, Git process, обход, хеширование и
возврат из callback. Произвольный пользовательский callback нельзя прервать;
превышение обнаруживается после его возврата. Это не sandbox для потребителя.
Ошибка может случиться после уже выполненных callback (поздний blob, общий размер,
дедлайн или завершение процесса). Потребитель обязан писать в private staging /
транзакцию и публиковать только после успешного `Receipt`; при ошибке откатывать.
Тест с SQLite BLOB-колонкой демонстрирует пофайловую запись и rollback. Это не
интеграция с форматом или публикацией snapshot_v5.

## Синтетические проверки

`tests/v5_ingest.rs`: 4 200 выбранных BSL × 9 000 bytes = 37 800 000 bytes,
4 201 регулярный путь, 4 202 чтения; невыбранный blob 17 MiB. Повторный проход
проверяет тот же манифест и учёт bytes, каждый callback — исходные bytes/SHA-256,
грязный working tree игнорируется. R09 отказывает; новый путь проходит. Отдельно
проверяются новые entries, reads (до callbacks), total bytes, object bytes, trees,
все нулевые/запредельные настройки, дедлайн в чтении и после callback, mismatch tree,
SHA-1/SHA-256, подмена содержимого blob под исходным OID, symlink/gitlink,
некорректные/дублированные пути, запрещённый layout и ошибка потребителя.

Fixtures создаются в temp контейнера и удаляются RAII; исходники БСП/ERP не нужны.
Существующие тесты R09/S3/S4 запускаются неизменёнными в полном all-features suite.

## Следующий срез: XML 2.21, память и новый проверенный профиль

1. **Пофайловый bounded XML 2.21 API.** Вынести из `Xml221Subset::inspect` проверку
   одного файла с явными bytes/events/nodes/depth ceilings, сохранив UTF-8/BOM,
   encoding, DTD/PI, namespace/version и shape-проверки. Не заменять текущий legacy
   API и не повышать его константы. Вход — проверенные исходные bytes и path/OID/SHA.
   Один DOM на файл допустим при жёстком file/node ceiling; затем он освобождается.
   Отдельно ограничить общий XML bytes, objects/facts и количество диагностик.
2. **Coverage вместо ложного «разобрано».** Записывать для каждого выбранного XML
   `parsed_supported`, `unsupported_type` или ошибку (малформированный XML — отказ,
   не unsupported). Для неизвестного типа допустим только отдельный ограниченный
   envelope/coverage результат, без выдачи типизированных фактов. Сохранять исходные
   bytes и OID/SHA также для unsupported. Сводка числа/bytes файлов по статусам,
   правил выбора и поддержанного подмножества обязательна в профиле. Не вводить
   общий «полностью разобран» для текущих четырёх типов `Kind`.
3. **Межфайловые связи.** Писать компактные промежуточные факты в private SQLite,
   ограничить их числа/bytes/страницы. Второй детерминированный проход проверяет
   дубликаты UUID/имён, orphan/missing, пути модулей и связи. Не возвращать весь
   `BTreeMap<String,Vec<u8>>` через `xml_inputs`; не накапливать все DOM/исходники.
4. **XML 2.20 — отдельный gate.** Сейчас не поддерживать и не угадывать структуру.
   Только после локальной сверки реального формата на NucBox: зафиксировать namespace,
   версии/envelope, отличие сериализации и разрешённый обезличенный synthetic fixture.
   Никаких копий реальных BSP/ERP в облаке. После сверки — отдельный adapter/version,
   положительные и отрицательные тесты; legacy XML-валидацию не ослаблять.
5. **source_lines и lexical.** Текущий `derive_facts` остаётся отдельным блокером.
   Сделать пофайловый расчёт с явными per-source/total line/fact ceilings; проверять
   счётчик до INSERT, offsets хранить в bytes, покрыть BOM/CRLF/UTF-8/пустой файл/
   последнюю строку без LF. Вставлять ограниченными batches в транзакции, ограничить
   SQLite pages и временное место. Не собирать общий Vec строк/лексических фактов.
   Offline verify должен воспроизводить тот же пофайловый алгоритм из BLOB с теми же
   пределами, сравнивая канонические факты в ограниченной scratch-БД.
6. **Идентичность/читаемый профиль.** До подключения нового ingest определить новое
   имя и версию профиля (старый S3/S4 не переобозначать). Нормализованная сериализация
   build parameters включает эффективные Git ceilings (в том числе fixed depth/path/
   layout), выбор расширений/регистр, XML/lexical ceilings и версии алгоритмов,
   политику unsupported/coverage, line/fact/SQLite ceilings и deadline в целых ms.
   Эти параметры вместе с commit/tree и версиями входят в канонический snapshot_id.
   Не включать wall-clock timestamps, RSS и фактическое время выполнения в ID.
   Reader обязан понимать и проверять новый профиль, bounds/coverage и соответствие
   сохранённых limits допустимым ceilings; неизвестный профиль отвергается.
   Согласовать writer+reader+offline verify и миграцию нормализации до публикации.
7. **Приёмка интеграции.** Синтетика выше старых count/bytes, смешанные supported/
   unsupported XML, пограничные значения каждого лимита, воспроизводимый ID при
   одинаковых параметрах и изменённый ID при изменении нормализованных правил,
   rollback при позднем отказе/ENOSPC, измерения пика RSS и source_lines роста.
   Затем локальный прогон реальной БСП на NucBox с согласованными пределами;
   отдельно проверка ERP. Ни один из этих реальных прогонов здесь не выполнен.

## Результат проверки этого среза

Rust `1.85.1 (4eb161250 2025-03-15)`, host `x86_64-unknown-linux-gnu`:
`cargo test --locked` — **1 passed**; `cargo test --locked --all-features` —
**116 passed**, включая 6 новых ingest-тестов; `cargo fmt --all -- --check` и
`git diff --check` — успешно. Отдельный fixture с 4 200 пустыми BSL подтверждает
старый предел числа файлов независимо от bytes и успешный новый путь.

В managed sandbox `/` и `/tmp` отображались с UID 65534, что закономерно давало
`Permissions` в неизменённых S4 staging-тестах. Финальные обе команды выполнены
в том же контейнере вне UID-remapping sandbox, с настоящим root-owned `/` и
`TMPDIR=/workspace/test-tmp`. Проверки владельца/прав не изменялись и не отключались.
Независимое ревью и интеграция следующих срезов ещё не выполнены.
