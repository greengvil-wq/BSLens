# ADR-003. Ограниченное чтение точного Git tree

Статус: экспериментальный R03, отдельная ветка от принятого R02. Production gate закрыт.

## Контракт

`git_manifest::Manifest::read(repo, commit, limits)` принимает локальный обычный
репозиторий с каталогом `.git` и полный lowercase SHA из 40/64 hex-символов.
Ветки, теги, сокращённые SHA и revision expressions отвергаются до запуска Git.
Получаем объект типа commit, проверяем его Git hash, первую ссылку tree и границу
заголовка/сообщения, затем читаем exact tree и все перечисленные обычные файлы.
Для каждого commit/tree/blob независимо пересчитывается Git object identity с
заголовком `type size\0`, а для файлов дополнительно SHA256 содержимого.

Manifest хранит неизменяемые bytes, mode, path, oid, sha256 и точные commit/tree IDs.
Файлы отсортированы по case-sensitive UTF-8 адресам. Рабочие файлы, индекс, refs,
исходный HEAD/config/hooks не используются. Исполняемый Git mode 100755 — факт,
файл не запускается. Symlink/gitlink/неизвестные режимы, некорректный UTF-8 адрес,
дубликаты и небезопасные сегменты отвергаются. SHA256 Git repositories покрыты тестом.

`xml_inputs()` возвращает копии bytes только exact `.xml`/`.bsl` адресов для R02.
Это явный путь к typed XML layer, но не конструктор `ValidatedSnapshot`, SQLite writer
или production-снимка. Manifest не проверяет подпись автора/доверие к коммиту,
семантику сообщения, историю родителей или все допустимые commit headers. Проверяется
content-addressed связь commit → tree → blob; Git fsck всего репозитория не выполняется.
Пустое tree допустимо; XML-адаптер затем самостоятельно требует Configuration.xml.

## Изоляция Git и платформа

Общий публичный интерфейс не принимает executable, аргументы, подкоманды или env.
В отдельном `git_manifest/process.rs` backend для текущего Linux использует доверенный
системный `/usr/bin/git`. Наследованный PATH не выбирает исполняемый файл. Другие
платформы пока явно неподдержаны; для Windows нужен отдельно проверенный resolver,
правила junction/reparse points и управление процессами. Путь Linux не является
контрактом будущего MCP или общей настройкой ядра.

На каждый вызов создаётся private временный bare-каркас с фиксированным config
и правами каталога 0700. `GIT_OBJECT_DIRECTORY` указывает на проверенный локальный
objects-каталог. Исходный config не интерпретируется; временный config содержит только
bare/repositoryformatversion и при необходимости objectformat=sha256.
Наследованная среда очищается, global/system config отключены, replace/lazy-fetch и
prompt запрещены. Рабочий каталог дочернего процесса — временный каркас.
Единственная производственная подкоманда — `cat-file --batch`; stdin содержит только
один проверенный OID. Нет shell, fetch, checkout, фильтров или внешних diff-команд.

Перед чтением отвергаются links/special files внутри objects, alternates/http-alternates
и promisor markers. Обычный bare repo и linked worktree пока не поддержаны. Временный
каркас удаляется RAII; исходный репозиторий не изменяется. Это не защита от враждебного
процесса, одновременно меняющего filesystem layout после проверки: объектное хранилище
должно оставаться стабильным. Побайтовая проверка hash обнаруживает подмену прочитанных
объектов, но не заменяет OS isolation от конкурентного злоумышленника.

## Бюджеты и жизнь процесса

По умолчанию: 4096 файлов, 8192 обращений к объектам, 8 MiB на один объект,
32 MiB совокупных распакованных объектов и 30 секунд общего времени.
Учитываются commit/tree и повторно прочитанные blobs, а не только сумма файлов.
Лимиты можно только уменьшать. Глубина tree/objects layout до 64, адрес до 1024 bytes,
предварительная проверка до 100000 entries объектного хранилища.

Stdout ограничен до выделения полного ответа; stderr не накапливается. Поток чтения
контролируется deadline, при ошибке/таймауте процесс убивается и забирается через wait,
поток присоединяется. Ожидание завершения после закрытия stdout тоже ограничено.
Внутренние тесты проверяют зависающий/неограниченно пишущий процесс; публичный API
не предоставляет этот тестовый механизм произвольного запуска.

Это намеренно не bulk API: по одному процессу на объект, без кэша и без обещания
скорости на БСП. Размеры и время проверены только на авторских данных Linux.
Дальше: независимое ревью, расширение adversarial corpus, отдельно Windows backend,
затем при необходимости bounded batch и измерения. MCP/SQLite writer/production open
в этот этап не входят.
