# S5–S6: автономный stdio MCP v5 и синтетическая приёмка

Статус: экспериментальный срез для ревью, не production-приёмка.
Точная база S4: `5c91f662ba6a398e841ba51b39cb3b6cd3d22c55`.
Платформа — Linux x86_64. Windows/ARM не поддержаны этим режимом.
S3/DDL/канонизация и старый R09 router не меняются. Новых зависимостей нет.

## S5: запуск и жизненный цикл

```sh
cargo build --locked --features experimental-snapshot-mcp --bin bslens-mcp --bin bslens-v5
# Сборщик вызывается только заранее, на синтетическом репозитории:
target/debug/bslens-v5 build /absolute/synthetic-repo FULL_COMMIT synthetic:demo /absolute/output 100 1000000 4000000 4000000
# FILE и SHA берутся из проверенного результата сборки; staging создаёт оператор:
mkdir -m 700 /absolute/private/staging
target/debug/bslens-mcp --snapshot /absolute/output/ID.SHA.sqlite \
  --staging-dir /absolute/private/staging --max-sqlite-bytes 4000000 \
  --expected-sha256 SHA
```

Числа здесь — только демонстрационные бюджеты синтетики, не настройки S8 или
промышленной эксплуатации. Вход и staging — абсолютные пути. Staging должен
соответствовать проверкам владельца и родителей [S4](adr-010-s4.md).
`--max-sqlite-bytes` обязателен и положителен; `--expected-sha256` необязателен,
при передаче снимка берётся из отдельной доверенной записи. Проверки SHA,
standalone-заголовка, схемы и приватной копии полностью выполняет reader S4.

Snapshot-режим отвергает `--repo`, `--commit`, cache-параметры, повторы и
неизвестные флаги до открытия файлов. Параметры snapshot-режима без `--snapshot`
также отвергаются. Без нового feature/на неподдержанной платформе режим возвращает
`snapshot_mode_unavailable`; переключения на Git нет.

Reader создаётся ровно один раз при запуске. До завершения сессии router владеет
той же read-only копией и read-транзакцией; каждый инструмент делает только SQL
чтение/срез BLOB. Путь снимка, Git, BSL-разбор и offline verify в инструментах не
вызываются. EOF/лимит сессии закрывает reader и удаляет только его копию.
После старта исходный файл может отсутствовать: reader продолжает читать копию.
Метаданные профиля/scope и ограниченная сводка покрытия кэшируются на сессию. Полное coverage читается один раз для сводки и не копируется в ответы.

Старый запуск `--repo ABSOLUTE_PATH --commit FULL_SHA` остаётся opt-in через
`experimental-router` и использует прежний R09 CoreSession. Новый feature включает
его лишь для совместимости бинаря; snapshot-ветка возвращается до Git-кода.
Сетевых портов, инструментов исполнения/записи, динамического переключения файлов
или репозиториев нет.

## Протокол и инструменты

Формат транспорта прежний: одно JSON-RPC сообщение на строку, UTF-8, LF как
разделитель; `Content-Length` не используется. Инициализация:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"demo","version":"1"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"metadata","arguments":{}}}
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"tree","arguments":{}}}
```

Объявлены только `metadata`, `tree`, `source` с readOnly/idempotent hints.
Успех: `result.isError=false`, `result.structuredContent={snapshot,data}`.
В `content[0].text` находится JSON с тем же объектом для текстовых MCP-клиентов.
Snapshot содержит `snapshot_id`, профиль, `scope_id`, временное `coverage`,
`relations=not_analyzed`, `git_provenance=not_verified`, `experimental=true`.
`coverage` в wire-ответе — сводка `summary_format=allowlist-v1`, а не исходный
coverage_draft. Сохраняются только u64-счётчики objects/modules/owner_unconfirmed,
accepted_modules/unparsed_modules и xml_unverified_count. Неточный тип или
отсутствующий счётчик дают null, а не выдуманный ноль. unparsed_modules вычисляется
как modules минус принятые при наличии корректных чисел. `details_omitted=true`
явно сообщает о пропуске подробностей. Пути, селекторы, неизвестные поля и причины
из произвольных расширений покрытия не выдаются. `coverage_sha256` — SHA-256
полного JSON покрытия после детерминированной сериализации serde_json, не хеш
исходных байтов поля и не доказательство истинности покрытия.
Это факты ограниченного разбора, без утверждений о семантике кода.

Поле `tools/call.params.arguments` необязательно: его отсутствие равно `{}`.
Поэтому metadata и корневой tree работают без arguments. Явные null/массив/строка/
число/bool остаются ошибкой -32602; source без обязательных полей также -32602.

`metadata {}` возвращает контекст и бюджеты API. `tree {}` открывает корень,
находит настоящий object_id конфигурации и возвращает одну полную ветку либо
отказ бюджета. Для продолжения скопируйте `items[i].children` в arguments следующего
`tree`: configuration/kind/object/module/unconfirmed. Не нужно выдумывать ID.
Вручную допустимы `level`, `parent_id`, `kind`, `module_path`, `max_nodes`.
Лишние/несовместимые аргументы отвергаются. Порядок — SQL S2: прямые модули
конфигурации, виды, неподтверждённые владельцы; методы — по начальной строке.
Объект без модулей остаётся виден. Метод возвращает сохранённые координаты, вид,
экспорт и готовые arguments `source`. Имена методов нормализованы лексикой R09;
оригинальный регистр остаётся в точных байтах `source`.

Ветка модуля содержит `status=accepted|unparsed`, `reason` и `items`.
Принятый модуль без методов: accepted, reason=null, items=[].
Непринятый: unparsed, стабильный код R09 (например Utf8/RegionHeader), items=[].
Отсутствующая ветка — отдельный `not_found`, не пустой успешный результат.

`source {path,start_line,end_line}` возвращает полные физические строки:
`line_units=physical_1_based_inclusive`, байты `byte_units=0_based_end_exclusive`,
`start_byte`, `end_byte`, `byte_length`, SHA-256 **среза**, parse_status/reason.
Путь — точный относительный путь сохранённого BSL; нет чтения из файловой системы.
BSL с отказом лексики читается так же. Диапазон токенов метода в `location` и полные
физические строки в `source` различаются: BOM, отступы и завершающий LF могут
быть вне лексического диапазона и внутри возвращённого среза.

## Точные байты и бюджеты

- `encoding="utf-8"`: `data` — строка, которую клиент кодирует UTF-8 без нормализации.
- `encoding="base64"`: `data` — стандартный RFC 4648 Base64 с `=` padding; сначала
  декодировать Base64, не трактовать данные как UTF-8.
- Нельзя удалять BOM, менять CRLF, добавлять LF в конце или применять lossy decoding.
  После декодирования проверить byte_length и при необходимости SHA-256 среза.

Контекст snapshot формируется по фиксированному списку полей и ограничен
12288 байтами сериализованного JSON до включения в MCP-ответ. `scope_id`
сохраняется точно, без сокращения или хеш-замены: максимум 1024 UTF-8-байта по S3,
а общий бюджет учитывает escaping. Лимит не позволяет неизвестным полям metadata
разрастаться на wire. Сам файл и profile/scope валидирует прежний reader S4.

Независимые уровни лимитов:

| Уровень | Политика | Отказ |
| --- | --- | --- |
| Вход SQLite | Обязательный доверенный CLI max-sqlite-bytes | snapshot_budget_exceeded при старте |
| S4/API | source ≤65536 сырых байт; tree ≤128 узлов и ≤32768 UTF-8-байт полей | tool budget_exceeded, без частичного payload |
| Транспорт | Весь сериализованный JSON-RPC body ≤65536 байт | JSON-RPC -32001, `Response exceeds byte limit` |

LF-разделитель транспорта не входит в body. Транспорт считает обе формы результата,
JSON-escaping, Base64 и конверт с ID; raw source меньше лимита ещё не гарантирует,
что ответ поместится. `content`/`structuredContent` дублируют данные для совместимости,
поэтому полезный объём меньше 65536. Отказ не обрезает содержимое, следующий запрос
в той же сессии разрешён. Клиент может запросить меньший диапазон. Если единственная
физическая строка не помещается, этот протокол не предлагает частичных строк.
Tree-пагинация не добавлена: превышение всей ветки — явный отказ.

Сохраняются лимиты транспорта R06: 1024 входных сообщений, 4 MiB входных данных
на сессию, уникальные ID и обязательный handshake. Это не глобальные RSS/CPU-лимиты.

## Машинные коды

До протокола: ненулевой exit status, stdout пуст, stderr содержит стабильный код
без исходников/путей: `snapshot_arguments`, `snapshot_version`, `snapshot_profile`,
`snapshot_checksum`, `snapshot_identity`, `snapshot_not_standalone`,
`snapshot_budget_exceeded`, `snapshot_integrity`, `snapshot_staging`,
`snapshot_rejected`. `snapshot_mode_unavailable` сопровождается причиной сборки.

После handshake: ошибки инструментов имеют `isError=true` и structuredContent
`{status:"error",code:...}`: `not_found`, `budget_exceeded`, `source_range`,
`snapshot_read_refused`. Неверные аргументы/инструмент — JSON-RPC -32602.
Превышение сериализованного ответа — JSON-RPC -32001; поля result и частичных
данных нет. Детали внутренних SQL/OS-ошибок не выдаются клиенту.

## S6: воспроизводимая синтетическая приёмка

```sh
cargo test --locked --all-features --test mcp_snapshot
cargo test --locked
cargo test --locked --all-features
cargo fmt --all -- --check
git diff --check
```

Тесты сами создают временный синтетический Git-репозиторий, строят S3-снимок,
запоминают нормализованное дерево R09 для сравнения и **удаляют только свой репозиторий**.
Фактический бинарь запускается с пустым PATH и без repo/commit. Проверяются
initialize → initialized → tools/list → metadata/tree/source → EOF, один staging-файл
до EOF, удаление исходного SQLite после старта, отсутствие повторного открытия,
совпадение порядка/покрытия дерева с R09 там, где контракты сопоставимы, прямые
модули, неподтверждённые владельцы, объект без модулей, отказанный и пустой по
методам BSL, координаты и exact bytes BOM/CRLF/last-no-LF/invalid-UTF8.

Отдельно проверяются raw-fit → JSON escaping overflow, raw-fit → Base64 expansion,
raw-fit → полный envelope overflow, сырой бюджет, стабильные коды/сообщения,
отсутствие частичного результата и возможность следующего небольшого запроса.
Тесты отказа запуска: v4, неизвестный профиль, неверная ожидаемая сумма,
повреждённый файл, смешанные режимы и повторные параметры.

## Что остаётся вне S6

S8 — реальные БСП/ERP, пиковая память/время, подбор лимитов и промышленная приёмка —
не выполнялся. NucBox/локальный рабочий компьютер не использовались, офлайн не
обходился. XML 2.20, Git-происхождение, связи/семантика, Windows/ARM и миграция v4
не заявляются. Ограничения загрузки произвольной схемы SQLite из S4 сохраняются:
проверки SQL-каталога не доказывают ограниченный RSS/CPU внутреннего разбора SQLite.

Результат проверки этого среза на Rust 1.85.1 в облачном Linux x86_64:
`cargo test --locked` — 1 passed; `--locked --all-features` — 116 passed.
Дополнительно `--locked --features experimental-router --test mcp_executable
--test mcp_snapshot_opt_in` — 6 passed: старый режим работает, snapshot без своего
feature отвергается без попытки Git fallback. `cargo fmt --all -- --check` и
`git diff --check` прошли. Защита владельца staging не ослаблялась: проверки,
которым нужен настоящий UID корневых каталогов, запускались вне отображения UID
файловой песочницы, как при приёмке S4.

Дополнение после независимого ревью: фактический stdio проверяет вызовы без
arguments и неправильные явные типы. Генератор S3 строит корректную фикстуру с
700 непроверенными XML-свойствами и coverage_draft >64 KiB: metadata, дерево и
однобайтовый source успешно укладываются в транспорт. Отдельная синтетическая
модификация вводит большие неизвестные поля, неверный тип счётчика и scope_id
из 1024 управляющих символов с пересчитанным snapshot_id; identity сохраняется,
данные не просачиваются в сводку, короткие ответы успешны. Слишком большой после
escaping ответ по-прежнему даёт ровно -32001 без result/частичного payload.
