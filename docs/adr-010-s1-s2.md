# ADR-010: контракт S1 и схема S2 автономного Linux v5

Статус: экспериментальный срез S1–S2 для ревью; исходный ADR-010 v6 остаётся
черновиком, production-приёмка не заявляется. Основание — ADR-010 v6.
База реализации — R09 `0f02baced9ab1e754ae45116227ee9bbd4998bd7`.

## S1: граница формата

Только Linux; WSL допустим на файловой системе Linux. Отдельный профиль
`linux-v5-spike-xml221-bsl-r09`, `metadata.schema_version = 5`,
`PRAGMA user_version = 5`, префикс `snapshot_id` — `bslens-v5-`.
Изменение PRAGMA возможно вне ограничений таблиц: будущий читатель обязан сверять
оба номера, профиль и точную схему. DDL сам по себе не валидатор входного файла.

v4 и профиль `synthetic-bsl-utf8-lines-v2` остаются только в `synthetic-dev`.
Миграции нет; v5 пересобирается из точного коммита. Будущий v5-читатель — отдельный
тип, взаимно отвергающий v4 и неизвестные профили явным кодом. В этом срезе читателя
нет и исполнение этого отказа не заявляется. `ValidatedSnapshot` остаётся закрытым;
Rust API, CLI, MCP и feature flags здесь не меняются.

`snapshot_id` описывает входы и параметры: отдельный `source_id`, полный commit OID,
tree OID, версии формата/ядра/адаптера/XML/лексики, профиль, `scope_id`,
нормализованные параметры. Это не хеш результатов разбора.
`facts_sha256` отдельно покрывает `objects`, `modules`, `methods`, `source_lines`
в будущем каноническом порядке. Вычисление обоих идентификаторов, канонизация
и хеш фактов не реализованы. Дата сборки хранится отдельно в
`metadata.built_at_utc` в UTC (`YYYY-MM-DDTHH:MM:SSZ`); она не входит ни в
детерминированный `snapshot_id`, ни в `facts_sha256`. Будущий S3 записывает фактическую
дату сборки; фиксированная дата используется только в синтетической фикстуре. В фикстуре ID явно тестовый, commit/tree — нулевые
синтетические значения, `facts_sha256 = NULL`: это незавершённый тестовый снимок,
который будущий публикующий сборщик/читатель должен отвергать. SHA-256 и Git blob OID
источников вычисляются лишь для проверки точных синтетических байтов.

## S2: модель и границы SQL

Исполняемый [DDL](../spikes/linux-v5/schema.sql) содержит ровно шесть таблиц:

| Таблица | Контракт |
| --- | --- |
| `metadata` | Одна строка с ключом 1, версия, профиль, входы, версии компонентов, параметры, манифест выбранных/исключённых входов, временное покрытие, лимиты и `relations = not_analyzed` |
| `sources` | Уникальный относительный путь, тип XML/BSL, Git mode обычного файла, blob OID, SHA-256 и точный BLOB |
| `objects` | Конфигурация/объекты: родитель, вид, имя и ссылка на сохранённый XML; объект без модулей допустим |
| `modules` | Путь BSL, nullable подтверждённый владелец, `accepted` или `unparsed`, стабильный код отказа из `lexical::Reason` R09 |
| `methods` | Только принятый модуль; имя, procedure/function, экспорт 0/1, физические строки и байтовые границы |
| `source_lines` | Индекс каждого сохранённого BSL, включая unparsed и неподтверждённого владельца |

`owner_id IS NULL` означает «владелец не подтверждён», независимо от статуса
лексики. `accepted` означает лишь принятие ограниченной лексикой, не семантическую
корректность 1С. `unparsed` требует код, не свободный текст; методы для него
запрещены составным FK. Изменение реестра причин потребует пересмотра профиля.

Строки 1-based, смещения 0-based, конец не включён. LF завершает физическую
строку; CR, LF и BOM входят в сохранённые байты, BOM принадлежит первой строке.
Последняя строка без LF сохраняется; после завершающего LF пустая строка не
добавляется; пустой BSL имеет ноль строк. Диапазон метода хранит точные лексические байты: от начала токена
`Процедура`/`Функция` до конца завершающего токена, как R09 `src/lexical.rs`.
BOM и начальный отступ перед заголовком, а также перевод строки после завершающего
токена в этот диапазон не входят. FK методов ссылаются только на номера начальной
и конечной физических строк. Проверка попадания `byte_start` в начальную строку и
`byte_end` в конечную строку, а также совпадения с токенами — ответственность S3/verify.
`source` отдельно возвращает полные физические строки по `source_lines`, как R09
`src/pipeline.rs`; равенство двух видов координат не требуется.

DDL обеспечивает типы (`STRICT`), локальные ограничения, уникальность, ссылочную
целостность и связи типов XML/BSL. Каждое пишущее соединение включает
`PRAGMA foreign_keys=ON` вне транзакции. Наличие metadata, полнота манифеста и
индекса, непрерывность строк, границы внутри BLOB, соответствие байтов хешам,
корректность XML/владельцев, отсутствие циклов объектов и совпадение фактов с
лексикой — проверки сборщика и verify, а не обещание одних CHECK/FK.
Тестовая фикстура проверяет полноту и непрерывность собственного индекса.
SQL предполагает SQLite с STRICT (3.37+) и функцией json_valid; проверено на 3.53.1.

Отдельной таблицы дерева нет. [branch.sql](../spikes/linux-v5/branch.sql) выбирает
один уровень: конфигурация → вид → объект → модуль → метод. Виды — виртуальные
узлы из `objects`. В корне, как в R09 `src/structure.rs`, сначала идут напрямую
принадлежащие конфигурации модули по пути, затем виды, затем обнаружимая группа
неподтверждённых владельцев (если они есть). Группа открывает ветку `unconfirmed`.
Методы упорядочены по физической начальной строке, как R09 `src/pipeline.rs`,
а не по имени. Текстовые ключи сортируются детерминированно BINARY. Статус и причина возвращаются на узлах модулей;
объект без модулей сохраняется в родительской ветке и даёт пустую дочернюю.
Это SQL-пример, не реализация пагинации или MCP.

[range.sql](../spikes/linux-v5/range.sql) получает только rowid и границы по
индексу. Тестовая утилита делает `blobopen`, `seek`, `read(end-start)` и не
сканирует исходник до запрошенной строки. Это демонстрация S2 на доверенной
фикстуре, не безопасный reader S4 для произвольного файла.

## Разделение следующих шагов

| Шаг | Ответственность |
| --- | --- |
| S2 (этот срез) | DDL, синтетические факты, минимальные SQL, тесты инвариантов и точных диапазонов |
| S3 (не реализован) | Git-входы точного коммита, разбор XML/BSL, вычисление ID и хеша фактов, полнота строк и манифеста, лимиты, сериализация публикаций, fsync и публикация самостоятельного SQLite без WAL/SHM/журнала; одинаковый ID не перезаписывается, различные факты — ошибка |
| S4 (не реализован) | Проверка Linux-путей и файловых дескрипторов; потоковое копирование в обязательный приватный staging; ожидаемая сумма до открытия SQLite; read-only/query-only/trusted_schema=OFF; схема, версии, ID, хеш фактов и FK; отдельный reader, доступ к диапазонам BLOB |
| S5 и далее (не реализованы) | verify по сохранённым XML/BSL, опциональная проверка происхождения Git, MCP, интеграционная приёмка и замеры |

S4 должен сверять имя `<snapshot_id>.<file_sha256>.sqlite` и metadata, учитывать
`--expected-sha256` из доверенной записи; подмена файла вместе с именем без
доверенной суммы не обнаруживается. Приватные файлы 0600 в owner-only каталоге
0700, без автоматической очистки чужих копий. `open` не разбирает BSL повторно;
`verify` пересчитывает факты и индекс. Хеши внутри файла не доказывают происхождение.

## Три вопроса остаются открытыми

1. Значения лимитов: `limits_draft` фикстуры содержит `defaults: null`.
   Ограничения кеша 40 MiB/4096 не превращаются в лимиты формата.
2. Конечный состав/представление покрытия: `coverage_draft` — временный JSON со
   счётчиками и `temporary: true`, не принятый контракт MCP и не полный SDD.
3. Формат/хранение внешней доверенной записи: здесь не определяются.
   `input_manifest` — перечень входов внутри снимка, не внешний доверенный манифест.

Связи не анализировались (`not_analyzed`); это не утверждение «связей нет».
БСП, ERP, XML 2.20, Windows и production-совместимость не проверялись.
