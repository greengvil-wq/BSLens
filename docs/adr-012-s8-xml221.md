# S8b: пофайловый frontend XML 2.21 с честным coverage

База: S8a `853f4720879d2f682f10617604deb295486d5a94`, PR #5.
Новая ветка: `spike/linux-v5-s8-xml221`. PR #5 не изменяется.

## Контракт и границы

Feature `experimental-v5-xml221` включает отдельный
`xml221::file::inspect(entry, expected_sha256, raw, limits)`.
Он пригоден для callback Git ingest и повторного расчёта из сохранённого BLOB,
но не подключён к S3 writer, S4 reader/verify, MCP или CLI. Это не новый проверенный
snapshot-профиль и не полноценный разбор БСП. Реальные исходники не использованы.

Вход — один XML blob, безопасный относительный путь, регулярный Git mode,
полный lowercase SHA-1/SHA-256 blob OID и ожидаемый SHA-256 исходных bytes.
После проверки размера frontend повторно проверяет оба хеша. Неверный хеш —
`Error::Identity` до XML-разбора. Связь path/blob с commit/tree подтверждает
вызывающий ingest, а не повторное хеширование само по себе.

`Inspection` содержит источник (path/mode/OID/SHA/число bytes), наблюдаемый
корневой QName и unqualified `version`, а также один из четырёх результатов:

| Analysis / coverage | Что действительно проверено |
|---|---|
| ObjectIdentity / `identity_only` | Envelope MDClasses MetaDataObject 2.21, ровно один поддержанный объект, локальные kind/name/UUID и соответствие иерархическому пути |
| UnsupportedType / `unsupported_type` | Тот же envelope 2.21, ровно один объект в MDClasses; записано только имя неизвестного типа, тело не интерпретировано |
| ServiceDocument / `service_document_unanalyzed` | Безопасный well-formed XML по служебному пути `ConfigDumpInfo.xml`; это классификация **по пути**, не подтверждение схемы документа |
| UnknownEnvelope / `unknown_envelope` | Безопасный well-formed XML с иным корнем/namespace; схема не реализована |

Поддержаны только Configuration, Catalog, Document, InformationRegister.
Из объекта извлекаются **только kind/name/UUID**. Отсутствуют поля «список модулей»
или «список детей»: пустой список не подменяет отсутствие анализа. Дополнительные
properties/attributes, ChildObjects, вложенные объекты и связи не анализируются;
`identity_only` остаётся частичным coverage даже для минимального документа.
Отдельный DTO не подтверждает уникальность UUID/имён во всём корпусе, наличие
Configuration.xml, ссылок, orphan/missing или принадлежность модулей.

MDClasses MetaDataObject обрабатывается раньше классификации служебного пути:
версия 2.20/2.22/отсутствующая, неверный envelope shape/namespace дочернего объекта
дают явный отказ, в том числе если файл назван ConfigDumpInfo.xml. Для служебного
и неизвестного envelope наблюдаемый `version` не интерпретируется как версия
выгрузки 1С: generic XML может иметь собственный атрибут version или не иметь его.
Это не разрешение анализировать metadata 2.20. Namespace с похожим именем root
не выдаётся за MDClasses; он получает unknown_envelope.

Синтаксическая ошибка в любом классе остаётся `Xml(Code::Malformed)`, а не coverage.
DTO не содержит копии исходника/DOM. Потребитель должен отдельно сохранить точные
исходные bytes также для unknown/unsupported/service вместе с хешами и coverage.

## Переиспользование защиты и лимиты

Legacy `Xml221Subset::inspect` и `State::read` не изменены. Прежняя приватная
`parse` теперь вызывает общий `parse_bounded` с прежними константами. Общая защита
не менялась: UTF-8/один BOM, запрет DTD и PI, только UTF-8 declaration encoding,
ограниченный event/depth проход quick-xml, затем roxmltree с запретом DTD и
node ceiling. Все эти проверки применяются и к неизвестным/служебным XML.

Caller обязан передать четыре положительных лимита не выше прежних потолков:
2 MiB source bytes, 10 000 DOM nodes, глубина 64, 20 000 quick-xml events.
Bytes включают BOM и исходные переводы строк; event count включает EOF;
node count использует правила roxmltree, включая document root.
Превышение настройки — `InvalidLimit{name}`, данных — прежний `Xml(Code::Limit)`.
Путь ограничен 1 024 UTF-8 bytes; разрешён только точный suffix `.xml`.

За один вызов удерживается один ограниченный DOM и компактный DTO. Здесь нет
корпусного накопителя. Отдельный wall-clock timeout frontend не вводится:
при вызове из ingest действует его общий дедлайн до/после callback, без возможности
прервать произвольный callback. Offline caller должен задать собственный бюджет
прохода. Per-file bounded работа не заменяет aggregate limits и ограничения SQLite.

## Минимальная основа writer/verify

`Limits::normalized_parameters()` возвращает детерминированный JSON эффективных
пределов и локальных правил: версия adapter `xml221-file-identity-v1`, namespace/
version metadata, список поддержанных типов, правила path/suffix/coverage и
служебного пути. Неверные limits отклоняются и здесь. Изменение каждого предела
меняет строку параметров. Это **фрагмент будущих build_parameters**, не snapshot_id
и не разрешение использовать прежний профиль S3/S4 с новыми правилами.

Следующий необходимый срез — ограниченный writer/verify и межфайловый проход:

1. Сохранять source bytes/OID/SHA, per-file DTO/coverage и параметры в private staging.
   До INSERT проверять общие files/bytes/objects/facts/coverage rows и SQLite pages.
2. Разрешать связи/проверять уникальность UUID, missing/orphan, ownership отдельным
   детерминированным проходом по индексам; не возвращаться к corpus BTreeMap bytes.
   Unsupported metadata не превращать в известные объекты с пустыми фактами.
3. Пофайлово ограничить lexical/source_lines, обрабатывать late errors/ENOSPC
   транзакционно. Offline verify повторно вызывает тот же frontend для BLOB,
   сверяет сохранённые DTO/coverage и межфайловые факты.
4. Определить новый полный профиль, включить XML параметры вместе с Git/lexical/
   SQLite limits в нормализацию snapshot_id. Reader должен явно понимать coverage
   и новый профиль. Сейчас существующие writer/reader его не принимают.
5. Полноценные служебные схемы, другие metadata types и XML 2.20 требуют отдельно
   подтверждённых форматов/синтетических fixtures; реальная локальная сверка на
   NucBox остаётся gate. Никакого угадывания ERP и изменения legacy-отказов.

Потолки этого среза могут остановить большой ConfigDumpInfo.xml или сложный объект;
их повышение и выбор production defaults требуют отдельной приёмки и замеров.

## Проверка классификации по документации

1C:Enterprise 8.3.27 Developer Guide, **2.17.4. Dumping** документирует отдельный
служебный файл ConfigDumpInfo.xml с информацией об именах/версиях объектов.
[Официальный источник](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_8.3.27_Developer_Guide/Chapter_2._Managing_configurations/2.17._Dumping_configurations_to_files_Restoring_configurations_from_files/2.17.4._Dumping/).
Проверка через GitHub-корпус `greengvil-wq/onec-platform-knowledge`, файл
`knowledge/guides/8.3.27/chapter-02.md`, commit
`aaff8858e8d2cf9119ef3f58416601a09f3e705a` (локальный индекс отсутствовал).
В прочитанном разделе нет контракта root QName/namespace этого файла; он здесь
не изобретён. Service fixture с `urn:synthetic` намеренно не имитирует реальную схему.

## Синтетическая приёмка

Тесты `tests/v5_xml221.rs`: идентичности всех четырёх fixture-типов совпадают с legacy;
SHA-1/SHA-256; BOM/комментарии; unknown type/service/unknown envelope; отказ metadata
2.20 и неверного envelope; malformed/encoding/DTD/PI/UTF-8; точные границы bytes/
nodes/events/depth; нулевые и запредельные настройки; path/mode/hash mismatch;
детерминированные параметры; явный partial coverage при неизвестном содержимом.
Сквозной тест: Git ingest → BLOB → удаление репозитория → пофайловый offline replay,
равенство DTO и отказ подменённых bytes. Это тест строительного блока, не v5 verify.

Проверено на Rust **1.85.1**, Linux x86_64: `cargo test --locked` — **1 passed**;
`cargo test --locked --all-features` — **124 passed** (116 унаследованных + 8 новых),
без warnings; `cargo fmt --all -- --check` и `git diff --check` — успешно.
Финальные тесты выполнены с `TMPDIR=/workspace/test-tmp` вне UID-remapping sandbox,
как в S8a: S4 требует настоящих доверенных владельцев `/`. Защита S4 не изменена.
GitHub CI, независимое ревью и реальные прогоны БСП/ERP здесь не выполнялись.
