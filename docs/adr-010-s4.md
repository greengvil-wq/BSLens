# S4: Linux reader и офлайн-проверка v5

Экспериментальный Linux API/CLI поверх S3. Не production capability и не
`ValidatedSnapshot`. База интеграции: S3 `a30d6e7a03421b3c592580303b18c9a9e2e32de8`.
DDL S2 остаётся неизменным. MCP, Windows и миграции v4 отсутствуют.

## Сборка и API

Rust 1.85.1; feature `experimental-snapshot-v5` включает сборщик и читатель.
Прежний `experimental-v5-reader` сохранён как alias.
`linux_v5_reader::LinuxSnapshotReader::open(path, staging, expected_sha256, max_bytes)`
возвращает отдельный читатель. `info()` показывает профиль, scope, временное
покрытие, `relations=not_analyzed` и `git_provenance=not_verified`.

Путь входа абсолютный; каждый компонент открывается через закреплённые
дескрипторы каталогов и `O_NOFOLLOW`, конечный файл также `O_RDONLY|O_NONBLOCK`.
Допускается только обычный файл в доверенном лимите. Копирование и SHA потоковые,
с повторной проверкой лимита при росте файла. SQLite никогда не получает входной
путь; неверная сумма отвергается до его вызова.

`--staging-dir` обязателен: существующий абсолютный каталог Linux 0700 текущего
UID, с проверенными родителями по политике R09. Копия создаётся exclusive 0600.
Сессия удаляет только свою копию после закрытия соединения, включая ошибки и
ENOSPC. Остатки после аварии имеют шаблон
`bslens-v5-reader-<pid>-<counter>.sqlite`; автоматической очистки чужих файлов нет.
Потребность в диске при open равна размеру снимка на каждую сессию.

После SHA: read-only SQLite, `query_only=ON`, `trusted_schema=OFF`, read-транзакция,
точная схема/версия/профиль, snapshot_id имени и metadata, пересчёт snapshot_id
общей функцией S3, FK, общий канонический facts_sha256 и совместимость scope.
`snapshot_id` — хеш входов с префиксом `bslens-v5-`, не UUID.
Иной совместимый непустой scope допустим и показывается потребителю.

Реестр схемы проверяется общим ограниченным валидатором: сначала число и длины
полей, затем построчное сравнение заимствованных байтов с фиксированным DDL.
Недоверенный реестр не собирается в Vec<String>. Текст metadata перед общими
JSON-проверками ограничен; источники и BSL при open не перечитываются в память
целиком и не разбираются заново.

`tree` требует `TreeLimits { rows, bytes }`: первый SQL-проход возвращает длины
полей и максимум rows+1 узлов; после проверки бюджета выполняется упорядоченная
выборка. Перед созданием строк бюджет проверяется повторно. `Limit` означает
отказ без частичного ответа. Байтовый бюджет относится к UTF-8 тексту пяти полей
узлов; rows ограничивает накладные расходы контейнеров. Это не точный предел RSS,
времени SQLite или сериализованного JSON с escaping и оболочкой metadata.

`source(path,start,end,max_bytes)` ищет границы по индексу и читает incremental
BLOB только для выбранного диапазона; работает и для непринятого BSL. Возвращает
исходные байты, включая BOM/CRLF и невалидный UTF-8, без изменения кодировки.

## Офлайн verify

`verify(snapshot_v5::Limits)` использует доверенные лимиты вызывающего кода:
количество источников, размер одного, суммарный объём и размер scratch SQLite.
Сохранённые значения лимитов сборщика не становятся политикой читателя.

В новом exclusive scratch-файле того же staging создаётся схема S2. Источники
копируются incremental BLOB по 64 KiB с проверкой SHA-256 и Git blob OID
(SHA-1/SHA-256 с Git-заголовком). Далее вызывается **тот же** `derive_facts`, что
в S3: XML-объекты и владельцы, BSL-методы и физические строки. Сравнение использует
единственную общую реализацию `facts_sha256`. Scratch закрывается и удаляется
после проверки, в том числе при отказе; файлов других сессий проверка не удаляет.

Разбор в verify наследует R09 XML-лимиты и реализацию S3, которая загружает
ограниченный суммарный корпус для XML-проекции. Это отдельная операция; такого
чтения на open нет. Disk-full и превышение scratch-лимита дают отказ, не успех.

Verify доказывает воспроизводимость фактов по сохранённым байтам. Даже совпадение
blob OID не доказывает существование заявленного Git-коммита. Проверки внешнего
Git-происхождения в этой команде нет.

## Команды

Сборщик сохраняет прежний синтаксис. Примеры чтения (пути и лимиты выбирает
оператор; production-значения по умолчанию не назначены):

```sh
bslens-v5 open /trusted/snapshot.sqlite --staging-dir /trusted/staging --max-sqlite-bytes 2000000 --expected-sha256 SHA
bslens-v5 tree /trusted/snapshot.sqlite --staging-dir /trusted/staging --max-sqlite-bytes 2000000 --level configuration --parent-id 1 --max-rows 100 --max-bytes 10000
bslens-v5 source /trusted/snapshot.sqlite --staging-dir /trusted/staging --max-sqlite-bytes 2000000 --path Unknown.bsl --start-line 1 --end-line 2 --max-bytes 4096
bslens-v5 verify /trusted/snapshot.sqlite --staging-dir /trusted/staging --max-sqlite-bytes 2000000 --max-sources 100 --max-source-bytes 1000000 --max-total-bytes 4000000 --max-scratch-bytes 2000000
```

Реальное имя файла обязательно `<snapshot_id>.<file_sha256>.sqlite`.
`--expected-sha256` необязателен для каждой команды чтения; он должен поступать
из отдельной доверенной записи. Расхождение с суммой имени также отвергается.
Без доверенной суммы замена файла вместе с именем не доказывает подмену.

`tree --level` поддерживает configuration/kind/object/unconfirmed/module;
родителя задаёт `--parent-id`, вид — `--kind`, модуль — `--module-path`.
Узлы объектов возвращают ключ для последующего `--parent-id`; исходная
конфигурация сборщика S3 имеет ID 1. `open/tree/verify` печатают JSON; `source` —
точные байты в stdout. Ошибки идут в stderr и дают ненулевой exit status.

## Проверки

Синтетическая интеграция: S3 build → удаление репозитория → open/tree/source/verify,
включая CLI с PATH без Git. Структурно допустимый неверный byte_start с корректными
хешами проходит open и отвергается verify. Проверяются SHA до SQLite, имя/ID,
неизвестный профиль, FK, испорченные факты, SHA/blob OID источников, совместимый
иной scope, лимиты metadata/scratch/tree, две сессии и ENOSPC через unit seam.

Тесты используют настоящий Linux UID родителей: файловая песочница облака
отображает владельца `/` и `/tmp` как 65534, поэтому для запуска синтетики
используется штатный облачный Linux вне этого отображения. Защита путей не
ослаблялась. БСП/ERP/NucBox и пользовательские выгрузки не использовались.

## Граница защиты SQLite

Проверки каталога выполняются SQL-запросами после открытия приватной копии.
SQLite может загружать и разбирать схему **до выполнения этих запросов**.
Лимит размера входного файла и bounded-каталог не являются доказательством
ограниченного RSS/CPU этого этапа и не защищают от всех ошибок самого SQLite.
Общая защита от произвольного враждебного SQLite-файла, process isolation и
ресурсные лимиты процесса не проверены и не заявляются. Рекомендуемая граница
этого спайка — доверенно полученный снимок с отдельно переданной SHA-256.

Используется единый bounded-валидатор S3 a30d6e7; копии валидатора в reader нет.
Тестовые seam-функции не входят в публичный API. ENOSPC вводится только закрытой
функцией stage_with в unit-тестах; публичный open всегда вызывает обычную запись.
