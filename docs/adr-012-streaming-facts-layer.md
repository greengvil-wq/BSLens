# Пофайловый producer: исходный библиотечный слой

> Документ фиксирует слой e3176f4. Его последующее подключение к новому профилю
> и CLI описано в [ADR-013](adr-013-streaming-profile.md); указанный ниже
> end-to-end барьер преодолён на синтетике, NestedUnsupported сохранён.

База: exact #9 `bf97d5e21ece847eda4b51cb0087e13eaef0935c`.
Этот шаг намеренно ограничен API `snapshot_v5::streaming_facts::derive` за отдельным
feature `experimental-streaming-facts`. Идентификатор алгоритма:
`sqlite-stream-facts-r09-v1`. **Это не имя принятого snapshot-профиля.**

## Результат и оставшаяся граница

Из уже сохранённых sources SQLite можно получить факты при более 4096 выбранных
BSL и более 32 MiB выбранных BSL, не восстанавливая Manifest/BTreeMap с телами
всего корпуса. Проверены отдельно 4200 пустых BSL и 9 BSL по 4 MiB. Старый producer
на тех же входах отказывает. Большие BSL сохраняют строки и статус `unparsed/Limit`,
а не ложное утверждение о распознанных методах: лексический предел остаётся прежним.

**End-to-end барьер пока остаётся.** Ни `build`, ни `build-ingest`, ни offline verify
не переключены на этот алгоритм. Старые профили, ID, DDL, reader/MCP и CLI-контракт
не изменены. Поэтому превышение обоих старых лимитов через фактический CLI и цепочка
нового профиля build → удаление Git → verify → MCP здесь не заявляются. Это следующий
атомарный интеграционный шаг: новое имя профиля/точный DDL, нормализация всех новых
бюджетов в ID, выбор общего producer в build и verify, проверка параметров в reader,
сквозная приёмка реальных бинарей. Публиковать снимки со старым именем профиля и
новым алгоритмом нельзя.

Причина разделения: корректный расчёт фактов и совместимость публикуемого формата
нуждаются в отдельных проверках; «поднять число» в старом профиле не решает обе задачи.
Этот API даёт проверяемую границу для следующего шага, а не готовый большой снимок.

## Вход, атомарность и ограничения

Вход — отдельная scratch SQLite с точной схемой v5, уже **закоммиченными** sources
и пустыми objects/modules/methods/source_lines. Активная внешняя транзакция отвергается:
при SQLITE_FULL SQLite способен откатить всю транзакцию, поэтому обещать сохранение
её незакоммиченных sources нельзя. API создаёт свой savepoint, при любой ошибке
откатывает все новые факты, sources сохраняются. metadata не создаётся, публикации нет.

Значения Limits обязательны и положительны; независимые экспериментальные потолки:

| Бюджет | Потолок |
|---|---:|
| sources count | 100 000 |
| один источник | 16 MiB |
| сумма исходных bytes | 512 MiB |
| полный SQLite | 1 GiB |
| facts: objects + modules + lines + methods + coverage entries | 2 000 000 |
| сериализованное покрытие | 1 MiB |
| кооперативное время | 300 секунд |

Это ограничение эксперимента, не результат замера БСП около 188 MB. Размер полного
SQLite ограничен `max_page_count` с учётом текущей страницы и уже сохранённых sources.
Более строгий прежний page cap не повышается. Установленный cap остаётся на scratch
соединении после вызова. При SQLITE_FULL возвращается ошибка SQLite, а не догадка
о том, была ли причина ENOSPC или ограничение страниц.

Пределы sources проверяются до копирования тел. Из SQLite читается ровно один
ограниченный исходник за раз. Объём входа не накапливается в Rust-памяти; остаются
компактные ссылки конфигурации/UUID/владельцы и ограниченные сведения coverage.
Позиции строк ограничены бюджетом фактов **до** построения массива. Бюджет заряжается
до INSERT; время проверяется между файлами, строками и методами. Deadline кооперативный:
он не прерывает один bounded XML/лексический разбор и отдельный SQL-вызов. Жёсткие
ограничения RSS/CPU процесса и обработка враждебного SQLite не заявляются.

Coverage использует консервативный верхний предел JSON-escaping при накоплении
селекторов; после сборки проверяется полный сериализованный JSON. Поэтому бюджет
может отвергнуть результат раньше его фактической wire-длины. MCP cap к этому
слою не относится и при интеграции должен остаться отдельным.

## Общая семантика с legacy

XML-код выделен в однодокументный метод того же парсера: namespace/version/DTD/PI,
UTF-8/BOM, scalar/UUID/name, ограничение XML 2 MiB, events/depth/nodes, неизвестные
типы и **NestedUnsupported остаются строгими отказами**. Legacy рекурсивный обход
и его порядок отказов сохранены. Новый слой читает Configuration.xml, затем его
ссылки по сортированному пути; проверяет межфайловые UUID, наличие ссылок и orphan
XML. При недопустимых входах точный порядок первой ошибки двух API может различаться;
оба отказывают. Отсутствующее знание не превращается в пустое покрытие.

Один общий BSL producer используется старым и новым путём: physical lines, byte
ranges, lexical status/reason и методы. Владельцы определяются только точными
известными путями модулей; прямые модули конфигурации имеют owner 1, неподтверждённые
сохраняются без владельца. Идентификаторы объектов следуют прежнему порядку путей.
Проверены равенство canonical facts_sha256 и coverage со старым producer на общей
фикстуре, BOM/CRLF/последняя строка без LF, invalid UTF-8 и accepted-zero.

API считает факты, но не проверяет криптографическое происхождение sources. Он
рассчитан на scratch после проверки digest/OID вызывающим verify либо ingest.
Никакого утверждения о Git provenance, БСП или семантике BSL он не создаёт.

## Проверки

```sh
cargo test --locked --all-features --test streaming_facts
cargo test --locked
cargo test --locked --all-features
cargo fmt --all -- --check
git diff --check
```

Синтетические файлы SQLite закрываются и заново открываются перед расчётом;
тест не зависит от Git. Отдельно проверены count и bytes сверх старых потолков,
точные границы count/total/per-file/facts, поздний facts-budget и SQLite page cap
с откатом всех фактов, coverage-budget, deadline, дубликат UUID, missing/orphan XML,
NestedUnsupported и запрет внешней транзакции. Старые CLI/MCP тесты запускаются
полным all-features suite; они не являются приёмкой нового алгоритма через CLI.

Рабочие базы, реальные БСП/ERP, Git пользователя и NucBox не использовались.
Новая публикация/PR в этом шаге не выполняется: кандидат остаётся отдельной локальной
веткой для независимого ревью; предыдущее ограничение публикации не обходится.

Облачный Linux x86_64, Rust `1.85.1 (4eb161250 2025-03-15)`:
`cargo test --locked` — 1 passed; `cargo test --locked --all-features` — 131 passed,
включая 7 новых тестов слоя. `cargo fmt --all -- --check` и `git diff --check` —
успешно; предупреждений нет. Полный набор со строгими staging-тестами выполнен
в том же облачном Linux вне UID-remapping sandbox, без ослабления проверок путей.
