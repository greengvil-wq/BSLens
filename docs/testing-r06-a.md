# Проверки R06-A

Авторские тесты библиотечного транспорта. Реальный MCP binary, запуск пользовательского
процесса и вызовы ядра в этот этап не входят.

Покрытие:

- согласование версии, последовательность initialize/initialized, ping, пустой tools/list;
- ранние/повторные/ошибочные переходы, неизвестные методы и отсутствие tools/call router;
- уведомления без ответов и без побочных переходов состояния;
- signed i64/строковые IDs, повторные IDs, запрет null/bool/float/экспоненты/-0;
- неизвестный ID пропущен в ошибке, нигде не подставляется null;
- duplicate keys на верхнем/вложенном уровне, Unicode-escaped дубликаты;
- invalid UTF-8/JSON, NaN, trailing data, JSON batch, чужой response envelope;
- глубина JSON, точный предел frame, переполнение и отсутствие завершающего LF;
- CRLF, несколько сообщений, EOF, отсутствие ответов на корректные notifications;
- общий лимит количества/байтов, включая notification flood;
- проверка размера полного выходного envelope до записи;
- ошибки чтения, записи и flush возвращаются как io::Error и закрывают сессию.

Все проверки используют память и явно переданные потоки. Ошибки не содержат исходный
вход/host paths и не порождают traceback. Полноценное испытание stdout процесса будет
отдельной задачей после добавления binary. Ни доступ к БСП, ни Windows не проверялись.

Исполнено на изолированном Rust 1.85.1:

- `cargo test --offline --locked --features experimental-stdio`: 11 успешно
  (9 транспортных интеграционных, 1 проверка encoder, 1 production gate).
- `cargo test --offline --locked --all-features`: 56 успешно.
- `cargo test --offline --locked`: 1 успешно, экспериментальный транспорт выключен.
- `cargo fmt -- --check`, `git diff --check`: успешно.

В итоговых прогонах нет предупреждений компилятора. Cargo.lock добавляет только
прямую связь с уже закреплённой serde 1.0.229, версии пакетов не менялись.
Независимое ревью требуется отдельно.

## Проверка точной границы бюджета

Отдельный `mcp_transport_limits` использует BufRead sentinel: попытка чтения после
последней разрешённой строки немедленно проваливает тест вместо реального зависания.
Проверены ровно MAX_MESSAGES, ровно 4 MiB и полный write/flush последнего ответа;
непотребление уже поставленного в очередь сообщения за лимитом; остаток 7 bytes
с остановкой после восьмого byte без разбора/ответа/дочитывания; отсутствие oversized
ошибки при прямом handle_body после исчерпания обоих видов бюджета.

Итог после исправления границ: offline locked stdio-only **16 успешно**, all-features
**61 успешно**, default **1 успешно**; fmt/diff check успешны. Пять новых проверок
добавлены отдельно; остальные сценарии транспорта и ядра сохранены.
