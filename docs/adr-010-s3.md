# ADR-010 v6: S3 — сборщик Linux v5

Статус: экспериментальный Rust-срез поверх S1–S2
`b7de99ca9dd585aa8f06d3e95e54bfe1d3c50c19`. Не production-приёмка.
Схема S2 и существующий MCP не меняются. S4 reader и verify как команды здесь не
реализованы; `ValidatedSnapshot` остаётся закрытым.

## Запуск

Сборщик доступен только на Linux под feature `experimental-snapshot-v5`:

```sh
cargo run --locked --features experimental-snapshot-v5 --bin bslens-v5 -- \
  build /absolute/repository FULL_COMMIT source-id /absolute/private-output \
  MAX_SOURCES MAX_SOURCE_BYTES MAX_TOTAL_BYTES MAX_SQLITE_BYTES
```

Последние четыре параметра — обязательные целые числа, без производственных
значений по умолчанию. Путь вывода абсолютный, его последний каталог создаётся
0700, если отсутствует; существующий должен принадлежать текущему пользователю
и иметь 0700. Родители проверяются как в R09 cache: root/current UID, без
групповой/общей записи, исключение — root-owned sticky каталог. Symlink-компоненты
не допускаются. Файлы создаются 0600. Одноимённый чужой файл не заменяется.

Rust API: `snapshot_v5::build(repo, commit, source_id, output, limits)` возвращает
путь, `snapshot_id`, `facts_sha256`, SHA-256 файла и признак `reused`.

## Входы и ограниченное покрытие

`Manifest::read` R09 проверяет полный SHA коммита, точный tree и Git blob OID,
читает Git object store, а не worktree. Ревизионные выражения вроде HEAD запрещены.
Выбираются все пути с регистрозависимым суффиксом `.xml`/`.bsl`. Выбранные пути,
mode и OID записаны в `input_manifest.selected`; остальные обычные файлы — в
`excluded` со стабильной причиной `NotXmlOrBsl`. Git symlink/submodule и неподдержанный
layout отвергаются существующим Git-контрактом, не маскируются как исключения.

XML 2.21 разбирает существующий `Xml221Subset`; конфигурация, объекты и подтверждённые
владельцы модулей происходят из него. Любой сохранённый BSL имеет module-строку,
даже без подтверждённого владельца. Объекты без модулей сохраняются.
`coverage_draft` содержит `temporary`, числа объектов/модулей, неподтверждённых
владельцев, счётчики принятых модулей/стабильных причин и XML unverified-селекторы.
`relations` и `semantics` явно `not_analyzed`. Конечная форма покрытия не принята.

R09-лексика выполняется один раз на модуль, all-or-nothing. Отказ сохраняет
`unparsed` и точный код `lexical::Reason`, методы не записываются. Строки индексируются
из исходных байтов независимо от UTF-8 и результата лексики. Принятые имена/границы
сохраняются в представлении R09, включая нормализацию имён лексикой. Экспорт
извлекается из последнего токена уже принятого узкого заголовка; нового парсера нет.
Байты методов — лексические границы; `source_lines` — полные физические строки.
Сборщик проверяет попадание лексических границ в соответствующие строки.

Четыре лимита S3 независимы от кеша: число выбранных файлов, размер одного,
суммарный размер выбранных исходников и размер SQLite. Нарушение выдаёт
`Limit { name, maximum, actual }` и не оставляет опубликованный файл. Для SQLite
ограничен `max_page_count` при размере страницы 4096, поэтому предел округляется
вниз до полной страницы. SQLITE_FULL не позволяет надёжно отличить ENOSPC от
достижения max_page_count: возвращается отдельный `SqliteFull { path, sqlite_bytes,
max_pages }` с диагностикой «диск или лимит страниц», без утверждения о причине
и без вымышленного actual. Временный файл удаляется, публикация не выполняется.

Дополнительно **сохраняются защитные ограничения R09**, это не новые значения
лимитов формата: Git читает все обычные blobs с существующими пределами (4096 файлов,
32 MiB суммарных Git-объектов, 8 MiB одного объекта, 8192 объектов, 30 секунд;
пределы layout/path/depth остаются прежними). XML-адаптер ограничен 4096 входами,
32 MiB суммарно, 2 MiB на XML и своими depth/event/node-порогами. Лексика ограничена
1 MiB, 65536 строками, 100000 токенами, глубиной областей 64. Эти отказы помечены
подсистемой `Git`/`Xml`; у R09 `Code::Limit` не содержит конкретного внутреннего
порога. В общем producer перед загрузкой BLOB дополнительно проверяются именованные
`xml221_r09_files` и `xml221_r09_total_bytes`. Увеличение четырёх лимитов S3 не
отключает старые guards. Проверка этих limits не означает поддержку реальной БСП/ERP;
расширение пределов старых подсистем — отдельная работа. 40 MiB лимит кеша не используется.

## Замороженная канонизация v1

Всё хеширование — SHA-256. Кодирование без JSON для самих таблиц: поток байтов,
без зависимости от порядка вставки, rowid, surrogate ID, страниц SQLite или даты.
Все длины/числа полей — unsigned 64-bit big-endian. Текст — точные UTF-8 байты,
без Unicode-нормализации. Типы различаются:

- `N` (один ASCII-байт) — NULL;
- `I` и signed 64-bit big-endian — SQLite INTEGER;
- `S`, длина, байты — SQLite TEXT.

REAL/BLOB в канонических проекциях запрещены. Каждая таблица: `T`, длина имени,
имя, число полей; затем для каждого поля `F`, длина имени, имя; затем строки:
`R`, типизированные значения в порядке полей; окончание таблицы `E`.
Пустая таблица всё равно содержит заголовок и `E`. Это различает поля/строки/таблицы,
NULL/пустой текст/числа и исключает неоднозначное склеивание значений.

Входной домен: точные байты `BSLens-v5/inputs/1\0`, где `\0` — нулевой байт.
Одна таблица `inputs`, одна строка, поля в следующем порядке:

`source_id, commit_oid, tree_oid, schema_version, core_version, adapter_version,
xml_version, lexical_version, profile, scope_id, build_parameters`.

`schema_version` — INTEGER; остальные TEXT. Нормализованные `build_parameters` —
compact JSON объекта с ключами в порядке BTreeMap (serde_json без preserve_order),
целыми значениями четырёх лимитов и фиксированными selection/git_guard/xml_guard/
lexical_guard. Несовпадение повторной сериализации JSON отвергается. Нет пользовательских
float-параметров. `snapshot_id = bslens-v5-` + lowercase hex входного SHA-256.
Не включаются дата, покрытие, манифест результатов, факты и физический SHA файла.
Полный commit/tree при этом связывает весь Git-вход, включая исключённые пути.

Домен фактов: `BSLens-v5/facts/1\0`. Таблицы и поля строго по порядку:

| Таблица | Поля канонической проекции | Порядок строк |
| --- | --- | --- |
| objects | xml_path, parent_xml_path, kind, name, source_kind | xml_path BINARY |
| modules | path, source_kind, owner_xml_path, parse_status, reason_code | path BINARY |
| methods | module_path, parse_status, kind, name, exported, start_line, end_line, byte_start, byte_end | module_path BINARY, start_line |
| source_lines | path, source_kind, line_number, byte_start, byte_end | path BINARY, line_number |

`parent_xml_path`/`owner_xml_path` разрешаются через FK; неподтверждённый владелец
и отсутствующий родитель — NULL. Идентификаторы objects/methods не хешируются.
`exported`, номера строк и смещения — INTEGER; остальные значения TEXT/NULL.
Перед хешем фактов выполняется `foreign_key_check`, чтобы сломанная ссылка не
превратилась в обычный NULL после LEFT JOIN. Хеш не доказывает семантику исходников.

Golden synthetic fixture из `tests/snapshot_v5.rs`:

- facts: `c84407ce028a22d8acb975d1c255280ed81eec64efa49a82267bae7bbb25a85d`;
- ID: `bslens-v5-4a945e206f7e08d35b51ed24f3f2dfcc5bf4a6ef2afd11237de06f668a4b2d5d`.

Git-дата фикстуры фиксирована. Дата реальной сборки берётся в UTC через SQLite
`strftime(...,'now')`; `built_at_utc` вне обоих логических хешей. Изменение только
даты меняет физический файл/SHA, но не snapshot_id/facts_sha256. Изменение факта
меняет facts_sha256, не ID; изменение source_id — ID, не факты.

## Публикация

Новый файл с уникальным именем создаётся O_EXCL/0600 в каталоге назначения.
DDL S2 включает DELETE journal. После транзакции соединение закрывается;
проверяется отсутствие WAL/SHM/rollback journal, проверяется размер; затем sync
файла и потоковый SHA-256 его байтов. Окончательное имя:
`<snapshot_id>.<file_sha256>.sqlite`.

Публикации одного ID сериализуются Linux `flock` на отдельном 0600 lock-файле.
Lock-файл сохраняется: удаление после unlock создало бы гонку двух inode.
Под блокировкой существующий файл не перезаписывается: проверяются SHA имени,
схема, ID и хеш его фактов; те же факты возвращают прежний путь с `reused=true`,
другие — `NonReproducible`. Изменившаяся дата новой сборки не заменяет прежний файл.
Несколько публикаций одного ID — конфликт, а не произвольный выбор.

Первичная публикация — `renameat2(RENAME_NOREPLACE)` в том же каталоге и sync
каталога. Даже неожиданно появившийся файл назначения не затирается. Временные
файлы текущей неудачной сборки и её sidecar-файлы удаляются RAII. Чужие временные
файлы не очищаются; после аварии могут остаться `.bslens-v5-*.tmp`.

Если sync каталога ошибся **после** успешного rename, результат честно возвращает
`PublishedSync { path, error }`: имя уже видно, crash-durability не подтверждена.
Автоматическое удаление или обещание «ничего не опубликовано» в этой точке неверны.
Повторный запуск проверит существующую публикацию. Приватный каталог защищает от
другого UID; процесс с тем же UID вне модели угроз, как в ADR.

## Общий API для S4 и будущего offline verify

Feature `experimental-snapshot-v5`, Linux; модуль `bslens_core::snapshot_v5`.
Тип ошибки `snapshot_v5::Error`, `Result<T> = std::result::Result<T, Error>`.
Для интерфейса с ошибкой String достаточно `.map_err(|e| e.to_string())`.

В `src/snapshot_v5/contract.rs`:

```rust
pub const SCHEMA: &str; // include_str! точного DDL S2, единственный источник
pub fn validate_schema_profile(db: &rusqlite::Connection) -> Result<()>;
pub fn compatible_scope(db: &rusqlite::Connection) -> Result<()>;
pub fn snapshot_id(db: &rusqlite::Connection) -> Result<String>;
pub fn facts_sha256(db: &rusqlite::Connection) -> Result<String>;
```

`validate_schema_profile` сверяет user_version, весь sqlite_schema (таблицы,
индексы, определения, отсутствие лишних view/trigger), единственную metadata,
schema_version/profile/relations. Недоверенный каталог не собирается в Vec:
сначала LIMIT ограничивает проверку числа строк эталонным числом плюс один;
далее проверяются типы и байтовые длины type/name/tbl_name/sql (максимумы из малого
доверенного DDL), только затем выполняется сортировка и построчное сравнение.
Это ограничивает копирование/сортировку результатов нашим кодом; внутренняя загрузка
схемы самим SQLite при prepare/open остаётся ответственностью ресурсных ограничений S4.

Перед чтением metadata как String/JSON проверяются единственность строки, типы
и `length(CAST(field AS BLOB))`, включая байты после NUL. Бюджеты текущего читательского
контракта: source_id/scope_id — 1024 байта, версии ядра/адаптера/лексики — 128,
xml_version — 16, profile — 64, snapshot_id — 74, UTC-дата — 20, OID/digest — 64,
relations — 32; JSON build_parameters — 16 KiB, coverage_draft — 1 MiB,
limits_draft — 4 KiB, input_manifest — 16 MiB. facts_sha256 пока допускает NULL
внутри сборки. Те же проверки выполняет snapshot_id до разбора параметров;
повторная публикация использует общий валидатор перед чтением ID/digest.
Бюджеты явно ограничивают экспериментальное чтение, не изменяют DDL S2 и не
закрывают вопрос конечного покрытия/лимитов формата. Вызывающий держит одну
read-транзакцию между проверкой длин и чтением значений.

`compatible_scope` дополнительно сверяет известные
версии ядра/адаптера/XML/лексики и временное покрытие; другой непустой scope_id
сам по себе не причина отказа. Покрытие читатель показывает потребителю.
Вызовы не открывают пути: S4 сначала обеспечивает свою безопасную приватную копию,
read-only/query-only/trusted_schema=OFF и одну read-транзакцию. После проверки
контракта он вычисляет ID/факты и сравнивает их с metadata/именем.

В `src/snapshot_v5/mod.rs`:

```rust
pub fn derive_facts(db: &rusqlite::Connection) -> Result<serde_json::Value>;
```

Это единственный producer фактов: S3 сам вызывает его после заполнения sources.
Для offline verify нужно создать **отдельную scratch БД** по SCHEMA, скопировать
в неё сохранённые sources, в транзакции вызвать derive_facts и сравнить facts_sha256
scratch БД с проверяемыми фактами. Producer требует пустые objects/modules/methods/
source_lines, не удаляет существующие факты, использует те же XML221/R09-парсеры и
возвращает временное покрытие. Он ограничивает count/sum BLOB до загрузки и работает
в памяти в пределах старых guards; это не обещание потокового verify. Хеши самих
sources и происхождение Git — отдельные проверки; producer их не доказывает.
Здесь нет CLI verify, безопасного reader или MCP и нет второго расчёта канонизации.

## Проверки этого среза

Только синтетические входы. Rust 1.85.1 (`4eb161250`, cargo `d73d2caf9`):

- `cargo test --locked --offline` — 1 тест;
- `cargo test --locked --offline --all-features` — 95 тестов, в том числе 12 новых
  интеграционных S3 и один unit-тест типизированного кодирования;
- `cargo fmt --check` — успешно;
- `python3 -m unittest discover -s spikes/linux-v5 -v` — 13/13 тестов S1–S2;
- `git diff --check` — успешно, Cargo.lock не изменён, новых зависимостей нет.

Внешний облачный executor отображает `/` и `/tmp` как UID 65534; прямой запуск
all-features закономерно отказал в старых R09 cache-тестах и S3-проверке родителей.
Проверки прав не ослаблялись. Полные тесты выполнены в штатном облачном Docker,
официальный `rust:1.85.1-bookworm`, digest
`sha256:e51d0265072d2d9d5d320f6a44dde6b9ef13653b035098febd68cce8fa7c0bc4`,
с обычными root-owned `/` и `/tmp`, без сети во время тестов. Rustfmt 1.8.0 из
официального закреплённого архива Rust 1.85.1 проверен отдельно (в образе нет этого
компонента); SHA-256 архива сверена с официальным файлом. Ничего не устанавливалось
на NucBox. Реальные выгрузки не использовались.

Ревью первого SHA S3: дополнительно проверены избыточное число строк каталога,
SQL определения размером 1 MiB при неизменном числе объектов, oversized metadata
(включая NUL и каждый переменный JSON), нейтральная диагностика SQLITE_FULL и
отсутствие опубликованных/временных файлов при этом отказе. Исходные golden-хеши
сохранены. Реальный ENOSPC искусственно не создавался: диагноз сознательно не
различает его и ограничение страниц.
