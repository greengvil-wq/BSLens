# ADR-055. Адаптер GitLab для чтения одного MR

Статус: **Предложено**. Разведка до кода; основа `3b02a450e3a67cf555192797a27ccf8537cf7b0c`. Реального сервера и данных нет. Ниже — проект контракта, а не описание работающей функциональности. Под «целевым коммитом приёмки» понимается head исходной ветки MR; это не head целевой ветки и не результат слияния.

## Что есть

- `src/git_manifest.rs:42` задаёт лимиты, `src/git_manifest.rs:141` читает манифест Git по репозиторию и коммиту; `src/git_manifest/process.rs:74` запускает фиксированный `/usr/bin/git`, а `src/git_manifest/process.rs:91` — `cat-file --batch`. ADR-007 (`docs/adr-007-git-batch.md:5`) описывает пакетное чтение в пределах одного манифеста. Это локальный Git, не GitLab-клиент. `src/git_manifest/ingest.rs:284` — отдельный путь ingest; `src/pipeline.rs:51` связывает структуру с коммитом.
- Транспорт разбирает `tools/list` и `tools/call` (`src/mcp_transport.rs:206`), а роутер предоставляет read-only `tree` и `source` (`src/mcp_router.rs:192`, `src/mcp_router.rs:208`); контракт транспорта и роутера описан в ADR-006. Источники содержат commit, scope, blob, путь и строки (`src/mcp_router.rs:66`), ответы — контекст и область (`src/mcp_router.rs:60`). Снимочный MCP открывает reader (`src/snapshot_mcp.rs:19`); reader проверяет идентичность и digest (`src/linux_v5_reader.rs:199`, `src/linux_v5_reader.rs:214`), но явно сообщает `git_provenance: not_verified` (`src/linux_v5_reader.rs:1047`). Новый результат адаптера не превращает это поле в доказанную provenance.
- Среди прямых зависимостей `Cargo.toml:24`–`Cargo.toml:32` нет HTTP-клиента. Выбор нового клиента, TLS и совместимости с Rust 1.85.1 требует отдельного решения. Существующие MCP-инструменты не предоставляют приёмку MR или доказательство отсутствия обновления поставщика.

## Модель и согласованность

Источники: [GitLab MR API](https://docs.gitlab.com/api/merge_requests/), [Branches API](https://docs.gitlab.com/api/branches/), [пагинация REST](https://docs.gitlab.com/api/rest/#pagination), [аутентификация](https://docs.gitlab.com/api/rest/authentication/). Версия сервера неизвестна: доступность полей и поведение лимитов должны проверяться на конкретной версии. `diff_refs` заполняется асинхронно; `base_sha`, `start_sha`, `head_sha` относятся к последней версии diff. `start_sha` — целевой коммит **на момент создания версии**, а не обязательно текущий head ветки. Версии фиксируются на push, не на каждый коммит.

Обозначим `P = /projects/:id/merge_requests/:iid`. `id` — числовой ID целевого проекта; IID — внутри него. Для форка сохраняем оба project ID и обе ветки; не предполагаем общий проект. Запросы только GET. Работать с уже подготовленным локальным репозиторием, содержащим полные объекты и историю обоих SHA; сетевой fetch и предоставление Git credentials вне области адаптера. Проверять соответствие локального репозитория доверенно заданному проекту отдельно: совпадение SHA само по себе не удостоверяет сервер. Не выполнять checkout и не читать рабочее дерево.

| Поле | Эндпоинт | Проверка локальным git | Исход при расхождении или отсутствии |
|---|---|---|---|
| project ID, IID, state, source/target project ID и ветки | `GET P` | Идентичность репозитория — явная доверенная конфигурация, не выводится из имени remote | `indeterminate`; удалённый source project допускается только если объекты и идентичность подтверждены; не-open MR — `indeterminate` |
| head приёмки | `P.sha`, `P.diff_refs.head_sha`, `GET P/versions` и `GET P/versions/:version_id` (`head_commit_sha`) | Полный SHA существует и имеет тип commit | Любое несовпадение, пустой diff_refs или отсутствие объекта → `indeterminate` |
| target branch и её текущий commit | `P.target_branch`, `GET /projects/:id/repository/branches/:branch` (`commit.id`) | Точный полный commit существует; имя не подменяется default branch | Отсутствие/несовпадение повторного чтения → `indeterminate` |
| base, start, head выбранной последней версии | `P.diff_refs`, `P/versions`, `P/versions/:version_id`: `base_commit_sha`, `start_commit_sha`, `head_commit_sha` | `git merge-base --all <start> <head>`: ровно один base и он совпадает с API; все объекты commit, полная история | Несовпадение, несколько base, shallow/неполный граф или недоступная версия → `indeterminate`; не считать start равным base |
| база для приёмки относительно текущей целевой ветки | branch commit и head выше | `git merge-base --all <target> <head>` — ровно один, совпадает с base версии | Иначе `indeterminate`: diff версии устарел или история неоднозначна; start может отличаться от текущего target, если base остаётся тем же |
| commits MR | `GET P/commits`, все страницы | Множество полных SHA сравнить с `git rev-list <base>..<head>`; проверить наличие объектов | Ошибка, неполная пагинация или несовпадение → `indeterminate`; порядок не является доказательством |
| изменённые пути | `GET P/diffs`, все страницы; old_path/new_path и флаги; конкретная версия — `P/versions/:version_id` как дополнительное свидетельство | Авторитетный набор — `git diff --name-status -z --no-renames <base> <head>`, оба пути при удалении/добавлении; сравнение с API после разворачивания rename в удаление+добавление | Неполный/ограниченный API diff, несовпадение, неподдержанный путь/тип → `indeterminate`, не частичный успех |

API diff может быть ограничен сервером, а версия иметь `overflow` или `without_files`; `collapsed`/`too_large` появились лишь в новых версиях. Отсутствие этих полей не доказывает полноту старого API. Считать полноту доказанной только при документированном для конкретной версии сервера механизме и успешном сравнении; иначе `indeterminate`. `changes_count` и число элементов первой страницы не являются доказательством полноты. Парсить пагинацию до её явного завершения, обнаруживать циклы и повторы; при лимите — отказ. Зафиксировать версии и branch перед выборкой, после выборки повторно прочитать MR, список версий и target branch; любое изменение идентичности, SHA, состояния или выбранной последней версии отменяет результат. Это обнаруживает обычные гонки, но не гарантирует атомарный снимок при ABA: результат привязан к наблюдаемым SHA и времени, а перед действием потребитель обязан повторить проверку. Нет заявлений о неизменности MR после ответа.

Пути сравниваются побайтно, без нормализации регистра и Unicode; для JSON v1 допускается только корректный UTF-8, относительные Git-пути без NUL. Вывод сортируется по байтам. Переименование — пара удаления и добавления без эвристики Git; API rename нормализуется так же. Для mode-only изменений учитывать путь; submodule, symlink, непредставимые пути и неизвестные статусы — `indeterminate`. Пустой diff допустим при подтверждённой полноте, но не считается доказательством отсутствия поставки без проверки метаданных ниже.

## Исключение обновления типовой

Это консервативная политика v1, не универсальное распознавание 1С. До её применения нужна явно заданная область корня конфигурации и поддерживаемый формат выгрузки. Читать BLOB из base и head, не рабочие файлы. Сравнивать только точно распознанные XML namespace и элементы; дубликат, неверная кодировка, отсутствие обязательного поля, неподдерживаемая схема или удаление/перемещение корня → `indeterminate`. Поля и допустимые расположения `Configuration.xml` и `ParentConfigurations` должны быть подтверждены синтетическими примерами и форматом конкретной выгрузки до реализации: произвольный текстовый поиск не является доказательством. Приведённые имена ниже — логические поля, не обещание XML XPath для всех форматов.

| Правило, вычисляемое кодом | Пример | Исход и доказательство |
|---|---|---|
| В подтверждённой паре Configuration.xml изменился распознанный идентификатор поставщика или версия поставки | provider A/version 1 → A/2 | `excluded_vendor_update`; путь, blob OID обеих сторон, поле и старое/новое значения |
| Изменился распознанный состав или версия записей `ParentConfigurations` | parent A/1 → A/2 | `excluded_vendor_update`, те же доказательства; сравнение канонических типизированных записей, не порядка XML |
| Метаданные корректны и перечисленные поля одинаковы; менее 100 изменённых путей и менее 20% файлов области, нет служебного признака | 3 из 1000 модулей, версия та же | `eligible` для следующей стадии, не утверждение, что обновления точно нет |
| Масштаб изменения: не менее 100 путей **и** не менее 20% файлов области в объединении деревьев base/head | 200 из 500 | `indeterminate`, число, знаменатель, пороги; масштаб не доказывает поставку |
| Изменён путь в явно настроенном списке служебных каталогов поставки | `vendor/service/a` при настроенном префиксе `vendor/service/` | `indeterminate`, путь и правило; имя каталога само по себе не доказывает обновление |
| Путь или метаданные недоступны, формат не подтверждён, знаменатель ноль, конфликт признаков | повреждён XML либо неизвестный ParentConfigurations | `indeterminate` с причиной; не молчаливый пропуск |

Масштаб считается по уникальным путям внутри настроенного корня, включая обе стороны rename; знаменатель — уникальные пути файлов в объединении двух деревьев того же корня. Пустой MR с ненулевым знаменателем и неизменной распознанной парой метаданных может быть `eligible`. Служебные префиксы задаются явно и по умолчанию пусты, а не угадываются по именам. При подтверждённом изменении поставщика `excluded_vendor_update` имеет приоритет над эвристиками; при неполных данных или расхождении Git/API сначала всегда `indeterminate`. Порог — предложение для обсуждения, не эмпирический факт; даже `eligible` не исключает ложного отрицания при нестандартном процессе поставки. Доказательства не содержат токенов и секретных HTTP-заголовков.

## Интерфейс

Предлагается отдельный модуль библиотеки с инъекцией read-only HTTP и Git-провайдеров, затем отдельная CLI-подкоманда; MCP не расширяется автоматически. Пример будущего API (именованные поля, без позиционных bool):

```rust
struct MrOptions { api_base: Url, project_id: u64, mr_iid: u64,
    repo: PathBuf, trusted_project: ProjectIdentity, config_root: PathBuf,
    vendor_dirs: Vec<PathBuf>, token: TokenSource, limits: Limits }
enum TokenSource { Environment { name: String }, File { path: PathBuf } }
struct Limits { connect_timeout: Duration, request_timeout: Duration,
    total_timeout: Duration, max_attempts: u32, max_pages: u32,
    max_response_bytes: u64, max_total_bytes: u64, max_paths: u64 }
fn inspect_mr(options: &MrOptions) -> Result<MrReport, AdapterError>;
```

CLI: `bslens gitlab inspect-mr --api-base URL --project-id ID --mr-iid IID --repo PATH --config-root PATH --token-env ENV_NAME` либо `--token-file PATH`; все параметры именованные. Файл токена и переменная исключают друг друга; секрет только в памяти, заголовке запроса, никогда в аргументах, URL, логах, ошибках и JSON. Запретить redirects на другой origin, URL с userinfo и небезопасный HTTP вне явно разрешённого mock-транспорта; не логировать тела API. Проверять сертификаты TLS. Токен с `read_api` и правами чтения обоих проектов; scope не заменяет членство/доступ и не используется для Git fetch. Никаких POST/PUT/PATCH/DELETE.

Начальные пределы: connect 5 с, запрос 30 с, весь вызов 120 с, до 3 попыток, до 100 страниц на endpoint по 100 записей, 8 МиБ на ответ, 64 МиБ суммарно, 100 000 путей. Ограничивать поток при чтении, включая декомпрессию. Повторять только GET при временных сетевых ошибках, 429 и 502/503/504 с ограниченным exponential backoff; `Retry-After` учитывать в пределах общего срока, при превышении вернуть `indeterminate`. 401/403/404 не повторять и не интерпретировать как пустой MR; все исчерпания лимитов — `indeterminate`. Отключить неограниченные автоматические повторы клиента.

JSON v1: `{ "schema_version": 1, "outcome": "eligible|excluded_vendor_update|indeterminate", "reason_codes": [], "mr": {"project_id": 1, "iid": 2, "source_project_id": 3, "source_branch": "feature", "target_branch": "release", "version_id": 4, "head_sha": "…", "start_sha": "…", "target_sha": "…", "base_sha": "…"}, "changed_paths": [], "evidence": [], "observed_at": "…" }`. Это схематический пример: outcome — одно значение enum, SHA полные; для неизвестных полей `null`, а не выдуманное значение. `changed_paths` — отсортированные записи `{path, change}`; evidence — типизированные записи с rule ID, путями, OID, значениями и счётчиками; `reason_codes` — стабильные коды. При `indeterminate` частичные данные помечены неполными и не пригодны к приёмке. Транспортная/конфигурационная ошибка также сериализуется как `indeterminate` без секрета; код выхода отличает его от определённых исходов. JSON — отдельный артефакт, не входит в снимки и digest.

Старые профили, схемы снимков и алгоритмы `facts_sha256` остаются без изменений; адаптер не пишет в них и не утверждает, что MCP-происхождение проверено. Фиксируются SHA и версия политики результата, чтобы потребитель мог проверить актуальность.

## Проверка на моках

Только синтетические фикстуры API и локальные временные Git-репозитории, без реальных данных; каждый сценарий проверяет outcome и evidence, отсутствие секретов в выводе и логах.

1. Несколько страниц версий, commits и diffs, включая rename, удаление и mode-only: совпадающий локальный diff → `eligible`, полный отсортированный набор. Повтор страницы, цикл, пропуск, усечение, overflow, исчерпание любого лимита → `indeterminate`.
2. 401/403/404 → `indeterminate` с разными кодами; 429 с Retry-After и успешным повтором → обычный результат, исчерпание срока/попыток → `indeterminate`; 503 и сетевой timeout аналогично. Нет попыток записи и утечки токена.
3. Форк: разные source/target project ID, все объекты доступны и идентичность подтверждена → `eligible`; нет доступа/объекта или подменён проект → `indeterminate`.
4. Несколько версий после force-push: выбирается последняя, SHA старой не принимаются; смена head/версии/target между чтениями → `indeterminate`. Пустой асинхронный diff_refs → `indeterminate`.
5. Пустой MR с полной историей и проверенными метаданными → `eligible`, пустые пути; отсутствие доказательства полноты → `indeterminate`. MR в `release`, не default: используется `release`, а не default.
6. Разные start и base при корректной истории → допустимо; устаревший base, несколько merge-base, shallow, отсутствующий объект, несовпадение набора commits или путей → `indeterminate`.
7. Каждое правило таблицы поставщика, границы 99/100 и 19/20%, повреждённый XML, изменение parent, служебный путь и конфликт → заявленный в таблице исход с точными доказательствами. Недоступные поля API старой версии, нестандартные пути, submodule и symlink → `indeterminate`.
8. Проверить запрет cross-origin redirect, лимиты распакованного тела, маскирование ошибок, только GET, отсутствие секретов в argv и выводе; повторная проверка идентичности перед передачей результата потребителю.

## Открытые развилки

1. **Полнота diff старых серверов:** доверять локальному Git без полной сверки API либо требовать доказуемую полноту API. Рекомендация — второе, иначе `indeterminate`: локальные объекты не доказывают, что API описывает ту же версию. Возможна низкая доступность на старом GitLab.
2. **Политика поставщика:** считать масштаб/служебный каталог исключением либо только сигналом неопределённости. Рекомендация — неопределённость, поскольку массовая собственная разработка не доказывает обновление. Подтверждённые поля поставки дают исключение; нужна проверка семантики конкретного формата.
3. **Устаревший target:** брать исторический start либо текущую ветку. Рекомендация — текущий target с проверкой совпадения merge-base версии; при расхождении ожидать пересчёта GitLab. Это избегает приёмки по устаревшей базе.
4. **Доставка объектов и HTTP:** выполнять fetch внутри адаптера или требовать подготовленный репозиторий; встроить HTTP-клиент в crate или выделить отдельный. Рекомендация — подготовленный репозиторий и отдельный модуль с инъекцией клиента: меньше полномочий, независимые моки. Отдельный crate и выбор TLS/клиента решить по совместимости с Rust 1.85.1.
5. **Атомарность:** повторные чтения или серверный механизм фиксации. Рекомендация — повторные чтения и обязательная перепроверка перед действием; они не устраняют ABA, поэтому сильная атомарность требует отдельного механизма.

Без пользователя нельзя определить редакцию и версию GitLab, URL, модель доступа и токен, идентичность проекта/локальной копии, формат и корень выгрузки, реальные пути служебных каталогов и семантику полей поставщика. Токен не запрашивается в ADR и не помещается в фикстуры.

## Реализация после разбора: три PR

1. Контракт и локальный Git: типы результата, проверка графа, путей и политики поставщика на синтетических репозиториях. Приёмка: все локальные граничные случаи дают ожидаемые три исхода, старые снимки и digest неизменны.
2. Read-only API и моки: ограниченный клиент, пагинация, версии, повторы, согласованность и доказательства. Приёмка: сценарии § «Проверка на моках», в том числе гонки и ошибки, проходят без реального сервера и секрета.
3. CLI и интеграция потребителя: именованные параметры, JSON v1, безопасная передача токена и повторная проверка перед действием. Приёмка: сквозные синтетические сценарии, проверка совместимости старых профилей и отсутствие изменений их `facts_sha256`; отдельная проверка с реальным GitLab только после предоставления пользователем параметров.
