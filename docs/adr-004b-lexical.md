# R04-B. Минимальные лексические границы методов

Статус: экспериментальная библиотека `lexical`, feature `experimental-lexical`.
Отдельный срез от принятого R04-A. Нет подключения к дереву, XML, Git, SQLite,
CLI или MCP; production остаётся закрытым. Вход — переданные авторские UTF-8 bytes,
не путь на диске. Это не полный перенос Python navigation и не парсер языка 1С.

## Подтверждаемый поднабор

- Однострочная шапка `Procedure Name()` / `Function Name()` и русские эквиваленты;
  необязательный `Export` / `Экспорт`. Параметры пока не поддержаны.
- Маркер конца соответствующего типа стоит отдельно на физической строке,
  допускаются отступы и комментарий. Точка с запятой после маркера пока запрещена.
- Имена нормализуются в нижний регистр: ASCII, русские буквы с Ё и `_`, цифры
  после первой буквы. Никакой Unicode-нормализации или транслитерации нет.
- Комментарий `//` и однострочная строка в двойных кавычках с удвоенными кавычками
  маскируются перед поиском границ. Ключевые слова внутри них не становятся методами.
- Скобки `()`/`[]` лексически балансируются. Тело не разбирается на операторы,
  вызовы или типы; корректность BSL-кода этим результатом НЕ подтверждается.

BOM допускается только в начале файла, LF и CRLF сохраняют исходные координаты.
`start_byte`/`end_byte` — 0-based UTF-8 offsets, конец исключён. Диапазон начинается
с ключевого слова, заканчивается концом closing keyword: отступы перед началом и
комментарий после конца не включены. Строки 1-based, физические, разделитель LF.
Отдельно возвращается диапазон шапки. Это координаты входного буфера, без доверенного
snapshot_id, пути или provenance. Повторяющиеся нормализованные имена не склеиваются:
каждое вхождение остаётся отдельной границей с собственными координатами и счётчиком.

## Отказы

Любая неизвестная/неподдержанная лексическая ситуация возвращает `Refusal` для
**всего модуля**, включая кандидатов до ошибки: partial success отсутствует.
Код причины и физическая строка доступны вызывающему коду.

- Условная компиляция и любые `#`-директивы: `DirectiveUnsupported`.
- Аннотации `&`: `AnnotationUnsupported`; `Async`/`Асинх`: `AsyncUnsupported`.
- Параметры, многострочные шапки, иной суффикс: `UnsupportedHeader`.
- Вложенные/перекрытые/не стоящие отдельно объявления: `AmbiguousBoundary`.
- Нет конца, неверный тип конца или скобки: `MissingEnd`, `UnmatchedEnd`, `Delimiters`.
- Многострочные строки: `MultilineString`; литералы даты в одинарных кавычках,
  неподдержанные символы вне строк/комментариев: `UnsupportedCharacter`.
- Неверный UTF-8: `Utf8`; лимиты: `Limit`.

Максимум 1 MiB входа, 65536 физических строк, 100000 токенов, 128 уровней скобок.
Пустой результат — только отсутствие найденных границ в этом поднаборе, не доказательство
отсутствия методов вообще. Режимы исключённых условных/async методов Python здесь
намеренно заменены более строгим отказом всего модуля.

## Авторское differential-сравнение

Внешний `bsl_navigation.analyze` использован только при подготовке JSON-векторов.
SHA256 файла внешнего эталона:
`3f151684c2d7346b6693c29e44e8f265120853288d46db40e7711f7fae20cd1b`.
Python не является runtime/build/test dependency и его код в проект не добавлен.

Пять положительных векторов в `tests/fixtures/lexical/oracle.json`: BOM/CRLF,
русский/английский, emoji в комментарии, строки и экранирование, скобки, нормализованные
дубликаты, пустой модуль. Rust проверяет точное совпадение всех координат, kind/name и
duplicate/occurrences. Три отрицательных вектора в `refusals.json`: conditional,
async и неоднозначный layout; ни один не становится подтверждённой границей.
Дополнительные тесты проверяют причины отказов, отсутствие частичных границ и caps.
Это небольшой общий авторский корпус, не полная эквивалентность Python и не БСП.

## Результаты исполнения

Изолированный Rust 1.85.1, облачный Linux, без пользовательской базы:

- `cargo test --locked --offline --all-features`: 24 теста успешно;
- `cargo test --locked --offline --features experimental-lexical`: 5 тестов успешно;
- `cargo test --locked --offline`: 1 тест успешно;
- `cargo fmt -- --check` и `git diff --check`: успешно.

В этом шаге не добавлены зависимости и не изменён Cargo.lock. Авторские проверки
не заменяют независимое ревью exact candidate. Windows/БСП не затрагивались.

## Уточнение после независимого ревью

До маскирования строк и комментариев проверяется **весь** UTF-8 буфер. Любой
Unicode control character (категория Cc), кроме TAB/LF и CR непосредственно перед LF,
даёт `InvalidControl` с физической строкой. NUL, DEL и C1 запрещены также внутри
комментариев и литералов. Одиночный CR запрещён везде, включая конец файла;
разрешён только CRLF, причём оба байта входят в исходную систему координат.
Это намеренное ужесточение относительно небольшого Python oracle, а не заявление
о полной паритетности его поведения.

Для имён дополнительно введён явный консервативный список основных управляющих
слов, логических операторов и литералов (`reserved_name` в коде, русский/английский).
Например, `Procedure If()` и `Процедура Если()` дают `ReservedName`. Список не
объявлен полным перечнем ключевых слов всех версий платформы; успешное имя всё ещё
не является compiler-grade проверкой. Проверка тела остаётся только лексической.

Добавлены проверки NUL/C0/DEL/C1 в комментарии и строке, одиночного/двойного CR,
корректного BOM/TAB/CRLF с координатами, зарезервированных имён и безопасных имён
с похожим префиксом. После исправления: all-features 26, lexical-only 7, default 1
тест успешно; locked/offline Rust 1.85.1, fmt/diff checks успешно.
