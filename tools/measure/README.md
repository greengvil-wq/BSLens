# Подготовка локальных замеров S8

Основание: ADR-010 v6 и SDD v0.3, §4/§8 (размер снимка с текстом/без него,
время и память). База утилит: S4 `5c91f662ba6a398e841ba51b39cb3b6cd3d22c55`.
«S7» — рабочее обозначение этой подготовки в текущем плане, **не найденная
формулировка или отдельный утверждённый этап ADR**. S8a и S8b ещё не проведены.

Продукт остаётся Rust. Здесь только Python stdlib для диагностики/экспериментов,
без изменений S3/S4/MCP и без новых зависимостей продукта. Linux x86_64;
Python 3.11+ (`sqlite3.blobopen`), Git, для продукта точный Rust 1.85.1.
Реальные исходники и все содержащие их файлы остаются локально на NucBox/WSL.
В облаке разрешена только специально созданная синтетика. Не коммитить, не
прикладывать к PR и не передавать модели пары БД, stdout продукта, репозитории
выгрузок или списки имён/путей. Утилита печатает только агрегаты и SHA, без argv,
исходников и путей объектов. Ошибки редактируются до стабильных кодов.

## 1. Preflight точного коммита

```sh
python3 tools/measure/measure.py preflight \
  --repo "$SOURCE_REPO" --commit "$FULL_COMMIT" > "$PRIVATE_RUN/preflight.json"
```

`SOURCE_REPO` и `FULL_COMMIT` пользователь задаёт **локально**. Полный lowercase
40/64-символьный SHA обязателен; HEAD/tag/ветка запрещены. Коммит проверяется через
Git `cat-file -t`, чтение `ls-tree -r -t -z`/`cat-file` идёт по его tree/blobs,
не по worktree. Репозиторий не меняется. Replacement refs/lazy fetch и глобальная
Git-конфигурация выключены. Это диагностика доверенного локального репозитория,
не повтор реализации проверок происхождения/безопасного Git reader R09.

Обработка потоковая: записи дерева ограничены 1 MiB, XML читается только до
первых 64 KiB для определения root/namespace/version, BSL-тексты не читаются.
XML DTD не раскрывается; нераспознанный префикс получает `other_or_unknown`.
Процессы/буферы не накапливаются на весь корпус. Предохранители самой диагностики:
`--max-entries 200000`, `--max-xml-scan 1073741824` суммарных байтов XML-префиксов,
`--seconds 300`; при исчерпании нет частичного результата с признаком готовности.
Это бюджеты диагностики, **не ослабление guards продукта**.

Выход содержит:

- число записей полного дерева, директорий, обычных файлов, неподдержанных
  mode/type и исключённых файлов; байты/максимум всех обычных файлов;
- отдельные count/sum/max выбранных `.xml` и `.bsl` (регистр значим);
- размер commit/tree/blob объектов по числу посещений R09, а не deduplicated pack;
- количество XML 2.21/2.20/неопределённых; отсутствие Configuration.xml;
- наблюдаемые превышения размеров, пути/глубины, список блокирующих guards.

Основные guards базы:

| Подсистема | Порог и влияние |
| --- | --- |
| Git R09 | 4096 обычных файлов, 8192 объекта, 32 MiB всех читаемых объектов, 8 MiB одного объекта; отказ до CLI-лимитов S3 |
| Git layout | 1024 байта пути, depth 64; отдельно runtime 30 секунд и ограничения object-store layout, которые preflight не доказывает |
| XML221 | 4096 выбранных XML+BSL, 32 MiB суммарно, 2 MiB/XML; только 2.21 и узкий набор структур |
| XML parse | depth 64, events 20000, nodes 10000; preflight не заменяет этот разбор |
| BSL lexical | 1 MiB, 65536 строк, 100000 токенов, region depth 64; отдельный модуль становится unparsed/Limit, это не обязательно отказ сборки |

`hard_blockers=[]` означает лишь `requires_build_and_verify`: нет доказательства
совместимости XML, полноты, успешной сборки или допустимой памяти. Ограничения
лексики по размеру отдельно в `lexical_size_refusals`, не выдаются за отсутствие
методов. Размер pack-файла/рабочего каталога не подставляется вместо Git object bytes.

**S8a, БСП.** Историческое свидетельство, не новый запуск: full — 12617
отслеживаемых записей, 3048 BSL, около 90 MB BSL; известный exact commit
`554b228b5b825908daf4b76afa5c77837bbc77cd`. Уже эти данные превышают 4096 и 32 MiB;
увеличение четырёх CLI-лимитов S3 этого не исправляет. После восстановления NucBox
заново подтвердить наличие этого коммита локальным preflight. Фактический путь
выгрузки намеренно не публикуется; задать его через SOURCE_REPO.

**S8b, ERP УХ.** Известно только историческое указание на XML 2.20. Exact SHA
неизвестен; наличие корректного Git-репозитория и файлов не подтверждено. Не
запускать команду с выдуманным SHA, не создавать Git автоматически. Сначала
локальная инвентаризация и явное решение о подготовке immutable Git-входа,
потом preflight. Поддержка XML 2.20 — отдельная работа по официальному формату и
авторским fixtures, не замена строки версии в XML и не догадка о совместимости.

Минимальные инженерные шаги перед реальными измерениями:

1. Зафиксировать точный состав и commit отдельно S8a/S8b; агрегатный preflight.
2. Отдельно спроектировать и проверить масштабирование Git/XML guards и памяти
   на увеличивающейся синтетике, сохранив отказ по лимитам. Здесь guards не сняты.
3. Для S8b — отдельный адаптер/подтверждённая поддержка 2.20 и отрицательные тесты.
4. Устранить неподдержанные XML-структуры честным расширением профиля либо явно
   согласовать ограниченный scope; subset-замер нельзя назвать full БСП/ERP.
5. Знак готовности к S8: preflight без известных критических blockers, успешные
   build/open/offline verify на exact SHA, зафиксированные версии/параметры,
   повторяемый facts_sha256, свободное место для оригинала/копий/scratch, закрытые
   технические блокеры. Только после этого собирать показатели и оценивать пороги.

## 2. Парный эксперимент SQLite

Сначала собственный сборщик создаёт immutable снимок и доверенную локальную
квитанцию с SHA. Успешно выполнить S4 open/verify. Затем:

```sh
python3 tools/measure/measure.py pair \
  --snapshot "$SNAPSHOT" --expected-sha256 "$FILE_SHA256" \
  --commit "$FULL_COMMIT" --workdir "$PRIVATE_RUN" \
  --max-bytes 1073741824 > "$PRIVATE_RUN/pair-report.json"
```

PRIVATE_RUN должен уже существовать, owner-only 0700, без symlink-компонентов и
небезопасных родителей. В WSL staging/output/PRIVATE_RUN — файловая система Linux
под `$HOME`, **не /mnt/c**. Каталог с префиксом `measurement-only-` создаётся 0700;
файлы 0600, marker MEASUREMENT_ONLY.json. После ошибочного запуска возможны
неполные локальные копии — не использовать; удалять только свою завершённую
экспериментальную директорию. Нет глобальной очистки чужих запусков.

Вход — только **доверенный снимок собственного сборщика**, не произвольный файл.
Ожидаемая SHA и commit сверяются, исходный файл открывается O_RDONLY/O_NOFOLLOW,
копируется потоково с бюджетом размера; WAL/SHM/journal рядом запрещены. Исходный
артефакт не открывается SQLite на запись и не изменяется. Это не повтор безопасного
S4 open: Python SQLite использует trusted_schema=ON на приватных копиях (в частности
SQLite 3.40 иначе отвергает json_valid в CHECK при VACUUM); загрузка extensions
выключена. Не использовать утилиту как валидатор недоверенных снимков.

Обе копии — **measurement-only**, даже полная. Имена специально не являются
именами опубликованных снимков: `measurement-only-with-bsl.db` и
`measurement-only-without-bsl.db`. Во второй только `sources.content` для BSL
заменяется на пустой BLOB. XML, paths/modes/OID/SHA, objects/modules/methods/
source_lines и metadata остаются идентичными. Встроенные хеши намеренно **не
пересчитываются и не подменяются**; безтекстовая ветвь невалидна для продукта.
Никогда не передавать её в MCP/verify и не выдавать за новый снимок.

Одинаковый эксперимент для обеих копий: одна Python SQLite version, page_size=4096,
auto_vacuum=NONE, journal_mode=DELETE, VACUUM, закрытие соединений. Потоковый
локальный контрольный digest проверяет равенство всех остальных фактов/метаданных
и XML; это не canonical facts_sha256 продукта. Оригинальный размер хранится
отдельно от обоих нормализованных размеров.

Отчёт различает:

- `original_bytes`: полный immutable артефакт сборщика;
- `normalized_with_bsl.bytes` и `normalized_without_bsl.bytes`;
- `paired_difference_bytes`: разность двух одинаково нормализованных БД —
  оценка стоимости BSL-текста при этой методике, не гарантированная экономия от
  удаления текста в исходном физическом файле;
- `raw_bsl_payload_bytes`: просто сумма BLOB-байтов, **не экономия SQLite**;
- `original_source_lines` и размеры source_lines в каждой копии: dbstat, включая
  таблицу и все её индексы, overflow/slack выделенных страниц. При отсутствии
  dbstat — `available=false, bytes=null`, без подстановки приблизительной цифры.

Разница может иметь страничное округление и даже неожиданный знак на маленьких
fixtures; она не является прогнозом для другой конфигурации, версии SQLite или
профиля сборки. Парный опыт хранит одинаковые XML/структуру/индекс строк, поэтому
не оценивает альтернативный формат без source_lines.

## 3. Время и память по отдельным операциям

```sh
python3 tools/measure/measure.py time --phase build --timeout 300 -- \
  "$BIN" build "$SOURCE_REPO" "$FULL_COMMIT" local-source "$FRESH_OUTPUT" \
  "$MAX_SOURCES" "$MAX_SOURCE_BYTES" "$MAX_TOTAL_BYTES" "$MAX_SQLITE_BYTES"

python3 tools/measure/measure.py time --phase open --timeout 300 -- \
  "$BIN" open "$SNAPSHOT" --staging-dir "$STAGING" \
  --max-sqlite-bytes "$MAX_SQLITE_BYTES" --expected-sha256 "$FILE_SHA256"

python3 tools/measure/measure.py time --phase verify --timeout 300 -- \
  "$BIN" verify "$SNAPSHOT" --staging-dir "$STAGING" \
  --max-sqlite-bytes "$MAX_SQLITE_BYTES" --expected-sha256 "$FILE_SHA256" \
  --max-sources "$MAX_SOURCES" --max-source-bytes "$MAX_SOURCE_BYTES" \
  --max-total-bytes "$MAX_TOTAL_BYTES" --max-scratch-bytes "$MAX_SQLITE_BYTES"
```

CLI подтверждён по exact S4. Каждое измерение — отдельный процесс; stdout/stderr
полностью отбрасываются, argv не записывается в отчёт. Код отказа сохраняется;
не смешивать failed build с успешным замером. Для build нужен новый приватный
output: повторный запуск в прежний каталог измеряет reuse, не полную публикацию.
`wall_seconds` — end-to-end команда, не внутренние фазы парсера. В частности
verify включает open и scratch/reparse; это явно не «чистое время verify минус open».
RSS — Linux wait4 ru_maxrss в KiB для этого вызова, не накопительный счётчик всех
предыдущих запусков и не сумма одновременно работающих дочерних процессов.
В него может попасть память дочернего процесса до exec, унаследованная от Python;
на малом примере это нижний предел метода, не точная память Rust. В отчёте есть
runner_peak_rss_kib_before_spawn и rss_floor_warning. Пики не вычитаются; при таком
предупреждении нельзя делать вывод о различии памяти фаз — нужен отдельный native
наблюдатель/profiler или достаточно крупный разрешённый синтетический workload.
Команда/драйвер должны синхронно завершать и ждать своих детей. Таймаут завершает
группу процессов; никаких сбросов page cache или настроек машины утилита не делает.

Зафиксировать release/debug, exact SHA продукта, Rust/SQLite, CPU/RAM/FS, один и тот
же source commit/профиль/лимиты, свободное место. Снять минимум три раздельных
повтора, сохранять порядок/состояние кэша: этот инструмент честно пишет
`cache_state=uncontrolled`. Не объявлять такой прогон cold-cache или оценкой CI.

После появления S5 можно передать `--phase first-tool -- DRIVER ...`. DRIVER
должен использовать реальный опубликованный MCP-контракт, дождаться initialize,
отправить выбранный первый tool и завершиться после ответа, закрыв сервер.
Формат S5 здесь не угадан, драйвера нет; без него first MCP/tool **не измерен**.
Для разделения startup/first-response драйверу нужны собственные монотонные метки;
внешняя wall-команда сама этих границ не определяет.

## 4. Воспроизведение и локальная подготовка NucBox

После восстановления соединения, без копирования реального корпуса в облако:

```sh
# Сначала подтвердить локальные repo/commit; для БСП известен исторический SHA.
export FULL_COMMIT=554b228b5b825908daf4b76afa5c77837bbc77cd
# SOURCE_REPO задайте локально; реальный путь не включён в документацию.
mkdir -m 700 "$HOME/bslens-measure-run" "$HOME/bslens-staging"
export PRIVATE_RUN="$HOME/bslens-measure-run" STAGING="$HOME/bslens-staging"
python3 tools/measure/measure.py preflight --repo "$SOURCE_REPO" --commit "$FULL_COMMIT"
# При blockers остановиться: текущий full БСП ожидаемо блокируется guards.
# Для ERP сначала установить реальный exact commit; приведённый BSP SHA неприменим.
```

Проверка программы и синтетики:

```sh
cargo +1.85.1 build --locked --features experimental-snapshot-v5 --bin bslens-v5
BSLENS_V5_BIN="$PWD/target/debug/bslens-v5" \
  python3 -m unittest discover -s tools/measure -v
cargo +1.85.1 test --locked
cargo +1.85.1 test --locked --all-features
cargo +1.85.1 fmt --check
```

Тесты создают собственный Git-репозиторий из авторских литералов S2, проверяют
неизменность worktree/оригинала, отсутствие имён в отчётах, формат 2.20 и размеры,
методику пары/dbstat, таймаут, реальную синтетическую сборку S3 и S4 open/verify.
Без BSLENS_V5_BIN последний интеграционный тест явно skipped; это не полный прогон.
`synthetic-results.json` — агрегаты одного debug-прогона на облачной синтетике,
только проверка работоспособности методики. Это не S8a/S8b и не производительность
реального корпуса. First MCP/tool не измерен.

Проверено в облачном Linux x86_64, официальном контейнере rust:1.85.1-bookworm,
Python 3.11.2 / SQLite 3.40.1, без сети во время тестов: 8/8 тестов измерительной
утилиты, включая реальный синтетический build/open/verify; Rust default 1 тест,
all-features 110 тестов; fmt/diff check успешны. Дополнительная синтетика с более
4096 файлов и 33 MiB исключённого blob подтверждает блокировку Git guards даже
при маленьком объёме выбранных XML/BSL. Внешний executor имеет UID 65534 у корневых
каталогов, поэтому для проверки приватных путей использован контейнер с обычными
Linux-владельцами, а сами проверки прав не ослаблялись.
